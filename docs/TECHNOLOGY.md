# GalacticAgents — Technology Recommendations

**Status:** Proposal v0.3 · **Date:** 2026-09-30 · **Client decisions:** React + React Three Fiber confirmed (Flutter set aside for the 3D client; a Flutter companion app for the side panel remains a possible later phase). Review decisions of 2026-09-30 incorporated: WebGL-only renderer for v1 (SPEC decision 20), Agent SDK adapter as the day-one Claude transport, brains run through that adapter, subscription login without `--bare` (decision 17), hard caps from Phase 1 (decision 18), simplified monorepo.

This document recommends a technology stack for the system described in `SPEC.md`, explains the reasoning, and lists the alternatives that were considered. The two constraints that shaped every choice:

1. **The agents are mixed CLIs** (Claude Code today; Codex, Gemini CLI, custom scripts later) running on the user's computer.
2. **The UI must eventually be reachable from a phone** while the computer runs the agents.

Constraint 2 rules out a "desktop app with everything inside it" design. The right shape is a **local server that owns the agents, plus a web UI that can be opened locally today and remotely later**.

The domain and event vocabulary used below is defined once, in `packages/protocol` (§7). Where this document and `IMPLEMENTATION_PLAN.md` name fields or events, they reference that package rather than restate it.

## 2. Recommended stack

### 2.1 Frontend: React 19 + React Three Fiber v9 + Three.js (WebGL)

**Recommendation:** React 19, [React Three Fiber v9](https://r3f.docs.pmnd.rs/tutorials/v9-migration-guide), `@react-three/drei`, `@react-three/postprocessing`, Three.js r17x with the classic **`WebGLRenderer`**, Zustand for state, Vite for tooling, TypeScript throughout.

Why this over Angular + Three.js (your daily stack): the "spectacular solar system" is the heart of this product, and the React 3D ecosystem is an order of magnitude larger. R3F gives declarative scene graphs that map naturally onto your domain (`<Planet>`, `<Satellite agent={…}>`, `<AsteroidBelt tasks={…}>`), drei provides camera controls, orbit helpers, HTML labels-in-3D, instancing helpers and loaders out of the box, and there are many open-source solar-system scenes to borrow from. Angular can host Three.js, but you would write all of that plumbing yourself, and Angular's change detection fights against a 60 fps render loop.

Rendering notes:

- **WebGL only in v1 (decision 20).** Three.js also ships a `WebGPURenderer` (with WebGL2 fallback), but it uses a different material/shader system (TSL node materials), and `@react-three/postprocessing` plus several drei helpers target the classic renderer. v1 needs nothing WebGPU offers (no compute shaders, no scene dense enough to need it), so one renderer, one quality matrix and the full helper ecosystem win. Keep hand-written GLSL to a minimum so a later move to WebGPU (GPU-driven belt simulation, say) stays feasible.
- The asteroid belt must be **instanced** (one draw call for thousands of rocks). Only the asteroids that host tasks get individual meshes/labels.
- Use `three-mesh-bvh` for fast raycasting/picking once the scene is dense.
- Level of detail (LOD) is mandatory: low-poly spheres at solar-system scale, textured spheres with bump/roughness detail maps when zoomed, and a separate "planet detail" sub-scene for surface/cutaway views. Do not try to render surface robots at solar-system zoom.
- Scale is fake: real orbital distances are unusable on a screen. Use logarithmic or hand-tuned spacing and keep a "true scale" toggle as a fun extra.
- Postprocessing: bloom for the sun and scanning beams, selective outline for the selected body. Keep a "reduced effects" quality tier for mobile.
- **Quality tiers** (P3-01, `apps/web/src/scene/quality.ts`, one table): `high` = DPR ≤ 2, MSAA, bloom 1.4, 9000 stars, shadows allowed; `balanced` = DPR ≤ 1.5, MSAA, bloom 1.0, 5000 stars, no shadows; `mobile` = DPR 1, no MSAA, no composer (a gradient sprite fakes the Sun's glow), 2000 stars, no shadows; belt rocks 6000 / 3500 / 1200 (P3-03). Bloom's luminance threshold is 1.0 (linear, before tone mapping): the Sun's emissive (≈ 1.95) blooms, the stars (capped at 0.85) never do. The tier comes from the server's settings (`qualityTier`, SPEC decision 51) and applies at once in this browser (another device's change after a reload); only a change of the context's antialiasing recreates the GL context. MSAA lives in the composer where there is one (`multisampling` 4); the context itself is multisampled only on a tier with MSAA and no composer (`contextAntialias`, P3-08: a multisampled canvas under a composer only resolved a full-screen quad).
- **Bodies and scale** (P3-02, `apps/web/src/scene/bodies/`, `scale.ts`, `motion.ts`; SPEC decision 63). Planets and moons are rendered from `world.bodies` (catalogue order `meta.orbit`, moons by `parentId`); a planet or moon made outside the catalogue (no `meta.orbit`: the early `/dev/seed` "Demo planet n") is drawn only while it hosts work or shows a "moved to …" marker, or one of its moons is drawn (`layout.ts` `drawn`, P4-13), so a free one has no anchor, label or pick target; dressed by a static per-name appearance table (style, palette, real radius and tilt, rings for Saturn and Uranus); unknown bodies get a default grey look. Surfaces are procedural `DataTexture`s painted at runtime from seeded 3D value noise: no image assets. Earth alone also has its real coastlines (P3-09, `earth-mask.ts`): a 1024 × 512 land/sea mask rasterised from Natural Earth's public-domain 1:50m land polygons by `apps/web/scripts/earth-mask.mjs` and committed as a run-length module (11 kB, in the scene chunk and the paint worker only). The painter samples it bilinearly from a small pyramid of averaged levels matching the texture size, with a noisy threshold along the coasts, then adds latitude biomes, a short table of arid regions (the deserts), ice on Antarctica, Greenland and the high Arctic, and shallow coastal seas. Equirectangular u = 0 is 180°W growing east and v = 0 the south pole, so on three's `SphereGeometry` the prime meridian faces local +X and the map is not mirrored. Earth's texture key carries the mask version (`EARTH_MASK_VERSION`). Fake scale is a monotonic AU → scene knot table (Mercury 16 … Neptune 192, so the belt at 2.2–3.3 AU lands at ≈ 52–66, between Mars's moons and Jupiter's); true scale is 35 units/AU with sizes and moon orbits ×≈85. The star-field shell (1200–2400) is centred on the camera just before it is drawn (`onBeforeRender`), so it is a real backdrop at any zoom and scale (the true-scale overview sits ≈ 2550 from the Sun on a landscape view). One orbit convention for every body (`scene/orbit.ts`): angle 0 on +x, counter-clockwise seen from +y, inclination lifts toward +y; placement writes into the object's position (no per-frame allocation). The frame loop is `always` while decorative motion runs and `demand` under `prefers-reduced-motion` (one shared `useReducedMotion` in `scene/motion.ts`). Shadows (P3-10, `bodies/eclipse.ts`, tiers with `shadows`) are **eclipse shading, not a shadow map**: each planet, moon and ring system is darkened in its own fragment shader by the casters of its **own planet system** only, the planet and its moons of real radius ≥ 1000 km (the Moon, the Galilean moons, Titan, Triton; at most 6 per system, largest first). The shader tests the ray from the fragment to the Sun against those spheres (centre and radius as uniforms, written in each receiving mesh's `onBeforeRender`, when every world matrix is current) and scales only the Sun's direct light, with a soft edge of `t × R_sun / d_sun` capped at a quarter of the caster's radius. So a moon's shadow is a spot its own size on its planet, the planet shades its rings and eclipses its moons, and a planet never eclipses another. The Sun's point-light cube shadow it replaces magnified every caster by d_receiver / d_caster; in the readable layout Mercury, Venus, Earth and Mars threw shadows wider than Jupiter, Saturn, Uranus and Neptune whenever they lined up, about 13 % of the time. The patch is one `onBeforeCompile` shared by every body material (one program, `customProgramCacheKey`), anchored on three's `common`, `project_vertex` and `lights_fragment_end` chunks; a test fails if three renames them. Rings cast nothing.
- **Asteroid belt** (P3-03, `apps/web/src/scene/belt/`). The asteroid generator (mulberry32, `BELT_SEED`, `BELT_ORBIT` = 2.2–3.3 AU and ±0.15 rad, `asteroidSpec(n)`) lives in `packages/protocol` (`belt.ts`): the server's catalogue names and places task asteroids with it, the client draws the decorative belt from the same seed and ranges. The background belt is one `InstancedMesh` (one jittered-icosahedron geometry, one material, per-instance scale, rotation and colour, a bounding sphere over all instances): one draw call whatever the count. Every rock takes a fixed number of PRNG draws, so a lighter tier draws a prefix of the same belt. Only asteroids that host work get individual meshes (rock, additive halo, an invisible pick sphere carrying `userData {bodyId, kind, hostId}`; their labels are the scene's domain labels, P3-07), and each registers its anchor. The belt's `phase` follows the scene's orbit convention (counter-clockwise seen from +y, like the planets); the protocol's phase is just a uniform angle. The rock count comes in as a prop from `SolarScene`'s quality object. The belt spins at 0.004 rad/s from `useFrame` delta.
- **Anchors** (Phase 3 wave 2, `scene/anchors.ts`): every rendered body registers the `Object3D` carrying its world position under its `Body.id` (the Sun under `b-sun`), with its visual radius at the current scale and a stable `order` within its kind (planets by catalogue orbit, moons by planet orbit × 1000 + rank, asteroids by `meta.number`); the camera, picking and labels find bodies only there. One shared binding (`scene/anchor-binding.ts`: `attachAnchor`, `useBodyAnchor`) registers them all.
- **Camera** (P3-04, `apps/web/src/scene/camera/`; SPEC decision 64): drei `OrbitControls` (damping 0.08) driven by a three-free `CameraDirector` (free / flying / following) that reads bodies only through the anchors. Requests go through a zustand `useCameraStore` (`flyTo(bodyId)`, `back()`, `next()`, `previous()`, `focusedId`), usable outside the canvas. Framing distance = radius / sin(0.3 × the narrower half FOV); flights are eased over 0.8–1.5 s; the approach keeps the current direction unless its line of sight passes within 1.5 Sun radii, else it turns to cos ≥ 0.3 away from the Sun; flights keep 2 Sun radii from the Sun and the camera 1.3. Next / previous go Sun, planets, moons, asteroids, each by the anchors' stable `order` (never by live distance). The overview frames the planets' orbits: the farthest non-moon anchor's distance plus its radius (× 3 for a planet); moons are ignored, so Nereid does not zoom true scale out. The rig reads anchors lazily: a free camera reads none per frame, a flight or a follow reads its one body, and the Sun radius and extent are cached until the anchors or the scale change. A released camera drops its pending request and a newly mounted rig ignores the request already in the store, so hiding and showing the scene or a tier switch never replays an old flight. The rig calls `invalidate()` during flights (needed when the loop is `demand`), raises `camera.far` with the zoom-out limit, and treats `prefers-reduced-motion` (the shared `scene/motion.ts` helper) as instant.
- **Picking** (`apps/web/src/scene/picking/`): ray vs the anchors' bounding spheres (centre + visual radius) with screen-space sizes measured at each body's depth — a minimum 6 px target, a 6 px cluster slop, and a 12 px "clear target" threshold below which several candidates open the "what's here" list. No mesh raycast and no `three-mesh-bvh`: about 40 spheres per pick, independent of LOD meshes; the instanced belt is not pickable. Pointer events are read on the canvas element (a release within 4 px of its press is a click; 10 px for touch and pen), hover is picked at most once per frame, on pointer moves and on camera moves. The selection outline is postprocessing's `Outline` (the composer runs with `autoClear={false}`) over the selected anchor's meshes, re-collected per frame (LOD-safe); it stays mounted, and its selection is empty for the default Harmonizer selection (Earth gets the ring instead), because a non-empty selection costs a depth pass over the whole scene every frame (about +70 draw calls at high). The mobile tier, without a composer, uses a camera-facing ring. Panel → scene sync flies only on user selection changes (`SelectionSync`). **Selection both ways** (P5-01; audit in `docs/tasks/notes/P5-01-selection.md`): every selection — navigation rows, card and history links, notifications, back/forward, the scene's picks — goes through the one `navigate` of the app store, so the URL follows every path; the sync flies for any change not made by the scene (`selectFromScene`) except to the Harmonizer. A selection that arrives together with a switch back to the panel's main view from a page without the scene (settings, history) is kept like a deep link (a module-level store subscription in `picking/sync.ts`) and flies once the scene mounts and the body is drawn; a change made in list mode does not fly when the scene is shown later. During a replay (P4-07) flights and picks use `sceneWorld` (the replayed world) while the panel shows the live agent; a panel selection whose agent has no body in the replayed world is dropped, not kept waiting (the camera never jumps mid-playback). Deselecting from the scene (`deselectFromScene`): a click release on empty space with no popover open (with one open, the click only closes it), or `Escape` once there is no popover and the camera is on no body — Escape unwinds popover → camera body → selection → whole-system framing; `Home` stays camera-only; the camera never moves on a deselect. **Satellites are pick targets** (P4-08, `picking/scene-pick.ts`; notes in `docs/tasks/notes/P4-08-satellite-hover.md`): each visible, present frame of `satellites/registry.ts` is one more sphere (its live `position`, half its `size`) with the same 6 px minimum target and no cluster slop; a satellite counts only when the ray passes through its target and its line of sight is not cut by a body's drawn sphere (a satellite behind its planet is hidden by it). A satellite under the pointer wins over the bodies that are clear targets (≥ 12 px, the planet it orbits seen up close) and over labels; of several, the nearest to the pointer on screen; when a speck of a body is under the pointer too (the system view), everything goes to the "what's here" list, satellites first in a stable order (role, then agent id — never per-frame screen distance), and the hover names the body with "+n", not a satellite that would change every frame. Hovering one shows its agent's card in place of the hover label (still one DOM element: `SatelliteHoverCard`, content from `satellite-card.ts` — the panel's `agentLabel`, the state pill, `StatusRecord.currentActivity` on one line cut at a word near 90 characters, the body and the mode when not plain orbiting); the card is positioned at the satellite's projected point and follows it: while any satellite is drawn (or one is hovered) and the pointer rests on the canvas the hover is re-picked once per frame, inside R3F's frame after the satellites' director wrote their positions (no one-frame lag); the hover's position is not in the picking store's React-selected state but in a separate channel (`moveHover` / `onHoverMove`) from which the card and the body label write their own `transform`, and the store's `hover` changes only when what is hovered (or its mode or "+n") does, so the overlay does not re-render at frame rate; the frame loop is invalidated only when the hover actually changed, so the `demand` loop still rests. **Hover grace** (`picking/hover-grace.ts`): a satellite picked by the rule above stays hovered (card and ring following it) while the pointer stays within 6 px of where it was picked, then, once the pointer has moved further, while the pointer is within max(the satellite's screen radius, 14 px) of its projected centre; it is released when the satellite is occluded by a body, off screen or gone (not visible / presence 0), when the popover opens, when the pointer leaves the canvas, or 3 s after the pointer last moved; off under reduced motion. The hovered satellite gets the faint camera-facing ring. A click on a satellite selects its agent (`waykeeper:<id>` / `steward:<id>`) and flies to its body (`activateSatellite`): the satellite hovered (or kept) at the press is activated on a click release without re-picking, as long as it is still visible and not occluded (it may have orbited out from under the pointer); the click-vs-drag rule is unchanged. Per-frame cost: the pick spheres, the ray and the anchors' positions live in scratch buffers reused from pick to pick (`anchorList()` / `satelliteFrames()` return the registries' own arrays, rebuilt only on register / publish), and the canvas's page rectangle is cached (dropped on resize, scroll, pointer re-entry and canvas size changes).
- **LOD** (P3-06, `scene/bodies/lod.ts`, `textures.ts`, `painter.ts`):
  - Each planet and moon picks a level from the tier's `lod` table by the camera's distance in body radii (so it works in both scales), with 15 % hysteresis.
  - A level swaps only the mesh's geometry (unit spheres per level, shared by all bodies, scaled by the mesh) and its material's maps. The anchor group is never replaced and its binding does not depend on the level.
  - The far map (256/128) is painted at once per body. Nearer maps are painted lazily in a Web Worker, one job at a time, and dropped if no longer wanted (the running one by terminating the worker). On a level change the body keeps its current maps until the new level's are ready. Without a worker, near maps are capped at the middle level's size with no detail map (no 2 s main-thread paints). Rocky and Earth-like surfaces also get an RG detail map from the same noise, used as `bumpMap` (R) and `roughnessMap` (G: glossy oceans; on Earth both follow the mask: relief only on land, gloss only on the sea).
  - Near maps live in a reference-counted cache keyed by content and size, kept idle within the tier's budget (96/32/8 MB, least recently used out) and dropped on a tier change. Not three's `LOD` / drei `<Detailed>`: those swap child objects, while a level here also means a lazily painted texture, and the anchor must stay put.
- **Quality tiers** add: LOD levels high 3 (2048 + detail near 16 radii, 1024 to 32), balanced 3 (1024 + detail near 12, 512 to 24), mobile 2 (512 near 12); ring segments 128/96/64; orbit segments 192·96 / 128·64 / 96·48; `labelHz` 30/30/15 (P3-07); `maxFps` 30 on mobile while motion runs: the loop switches to `never` and a rAF loop calls `advance()`, so even a camera follow is capped; the fps meter lifts the cap. Orbits run on their own clock (`motionSeconds`), since R3F's restarts on every loop change.
- **Domain labels** (P3-07, `apps/web/src/scene/labels/`; product text proposed in `docs/tasks/notes/P3-07-labels.md`). One DOM layer over the canvas, not a drei `Html` per body (each of those projects and writes its transform every frame). `label-model.ts` turns the world into labels with no three.js: a body hosting a project or task shows the work's name and its server-derived state (P2-15) as a pill, a planet or moon with only `movedTo` shows "moved to <body>" (an asteroid whose task moved away rejoins the belt, decision 63, and has no label), reserved (`star`, `meta.reserved`) and free bodies show nothing; a moon hosting a project is `sub-project` (the project has `parentProjectId`: "↳ part of <parent>") or `independent` (an "own project" badge, and `MoonMarkers.tsx` draws a teal camera-facing ring around it). `LabelLayer.tsx` (panel chunk) renders the content from the store, so a state change shows on the next React render; positions never go through React. `LabelProjector.tsx` (inside the canvas) runs in `useFrame` at most `labelHz` times a second (30 high/balanced, 15 mobile, never above the capped loop): it projects each label's anchor with one view-projection matrix, drops labels behind the camera, off screen (a label pushed above the viewport is hidden, except the selected and the camera-focused body's, which is clamped to the top edge), or whose line of sight passes through the Sun or a planet, de-clutters overlaps greedily by priority (selected > blocked on user > in progress > other open work > finished/moved; then nearer, then id), and writes a label's `transform` only when it moved more than 0.5 px and its `visibility` only when it changed. Content changes (a label is re-measured only when its title, state, moon role, parent, priority or selection changes), new labels, new or removed anchors (a label may register before its body's anchor) and resizes force the next pass; on the `demand` loop a skipped frame schedules one render for when the next pass is due. The layer and the projector meet in `registry.ts` (element, priority, size, last written position). The labels take no pointer events, so wheel, drag and click reach the canvas (OrbitControls, the click-vs-drag threshold); picking resolves label hits itself (`labelUnder`): a body the pointer's ray hits (its sphere or minimum target) wins, otherwise a shown label's rectangle under the pointer (`registry.labelAt`) means that label's body, over near misses — so a moon under its planet's label stays clickable. Stacking inside the scene area (custom properties on `.pnl-scene`, `scene.css`): canvas < labels < scene chrome (fps meter, breadcrumb, scale toggle) < hover label < popover. The layer is `aria-hidden`: labels are pointer-only extras, the panel carries the same information, the scene's keyboard path is `]` / `[` + `Enter`. Measured (headless Chrome, M3 Pro, 1440×900 at DPR 2, 41 labels): 60 fps on every tier with and without labels; ≈ 15 DOM writes/s at the overview, ≈ 90–150/s during camera flights (drei `Html` would have been ≈ 1 800/s).
- **Performance pass** (P3-08, numbers and the device-run steps in `docs/tasks/notes/P3-08-perf.md`). Decorations (orbit lines, the star field, task-asteroid halos, the highlight and own-project rings) live on their own layer; the belt's background rocks stay on layer 0 because they really hide task asteroids, and an outline is no longer hidden behind a halo (review) (`scene/layers.ts`, `DECOR_LAYER` = 1, enabled on the canvas camera at creation); the selection outline's depth pass, which re-renders the scene every frame a body is outlined, is wrapped to render without that layer, and the outline's selection is emptied while the selected body (its anchor sphere × 2.5, rings included) is outside the view frustum. Measured with 11 projects, 30 task asteroids and 42 labels (headless Chrome, ANGLE Metal, M3 Pro, 1440×900 at DPR 2): high with a Waykeeper selected 291 → 226 draw calls and 407k → 264k triangles at the system view, 82 → 57 with the selected body off screen; 60 fps (vsync) on high and balanced in every view, a steady 30 on capped mobile, no main-thread task over 50 ms, label passes invisible in the CPU profile. At high the GPU cost is pixels (DPR 2 × 4× MSAA HalfFloat composer, bloom, the cube shadow, since replaced by the cheaper eclipse shading of P3-10), not draw calls: DPR 1.5, fewer MSAA samples or no shadows are the levers if a Mac misses 60 (proposed, not applied). Each task asteroid costs about 2.5 draw calls; instancing them is the step if task counts pass about 100. Reaching the dev or preview server from a phone takes two per-run opt-ins: Vite's `--host` and `GALACTIC_ALLOWED_HOSTS=<the Mac's LAN IP>` (the server itself stays on `127.0.0.1`).
- **Renderer setup** (P3-01). The canvas's `gl` factory builds a `WebGLRenderer` explicitly (WebGL2: three 0.186 has no WebGL 1 path, so the up-front probe asks for `webgl2` only, and only when the scene is to be shown — list mode never probes); output is sRGB with ACES filmic tone mapping, which are R3F's own defaults and not set again. A `webglcontextlost` on the canvas is `preventDefault`ed and reported: the panel drops to list mode with a "Retry" that mounts a fresh canvas. The postprocessing composer forces `NoToneMapping` on the renderer, so with it ACES is the composer's last `ToneMapping` effect. The frame loop is `demand` until something moves; `?show_fps=true` on any panel URL shows a dev frame-rate meter at the scene's top-left (remembered per browser, `?show_fps=false` clears it) and switches the loop to `always`. The flag is taken when the app starts (`captureFpsFlag`, before the URL sync), and the panel's canonical URL rewrite (`navigate(…, { replace: true })`) keeps the query and hash: the scene mounts later, after the settings load (P3-11).
- **Bundle** (P3-01). three.js, R3F and postprocessing live in a lazily loaded `SolarScene` chunk (≈ 1 MB, 266 kB gzip); the panel's first chunk carries none of them, so list mode and a WebGL-less browser never download them. Versions: three 0.186 (postprocessing's peer range stops before 0.187), @react-three/fiber 9.8, @react-three/drei 10.7, @react-three/postprocessing 3.1, postprocessing 6.39.
- Satellites are animated actors with a small state machine (orbiting / scanning / gathering / transporting / building / flying-to-new-body / landing / landed), driven by the status store, so "work moved to Europa" and "task completed" are animations, not just label changes.
- **Satellites** (P4-01, `apps/web/src/scene/satellites/`; SPEC decision 68; notes in `docs/tasks/notes/P4-01-satellite.md`). One satellite per **live** Waykeeper and Steward: a status record whose state is not in `ENDED_STATES` — one predicate, `showsSatellite(world, id, { keepFailed, keepLanded })` in `satellite-model.ts`, both options off by default; the scene's choice is `SCENE_SATELLITES` (P4-02 turned on `keepFailed`: a failed agent keeps its satellite in its failure colour, see the next bullet; P4-04 turned on `keepLanded`: completed work's newest Steward or Waykeeper, no longer live, stays as `landed` until the work is archived or reopened — see the body transitions bullet); its body is the work's body (the project's for a Waykeeper, the task's for a Steward, falling back to `agent.bodyId`), so a move (`body.moved` + the server's `task/project/agent.updated`) changes it and the satellite flies. The Harmonizer's HQ station is a list option (`harmonizer: true`, on `b-earth`; on in the scene since P4-02). The actor is a pure state machine (`machine.ts`): `orbiting | scanning | gathering | transporting | building | flying | landing | landed`, a transition table that `advance(actor, input, now)` never leaves, and every timed step stored as absolute times on the motion clock (`motionSeconds`), so a flight (3 s) or landing (1.6 s) started while no frame is drawn has ended by the next frame; the director applies a world change at once (`setSpecs`), not at the next drawn frame. A flight runs to completion (only a new destination retargets it); landing and archetypes wait for the arrival. Inputs: `bodyId` and `state` (P4-01: a `working` agent scans every 5–10 s for 2.4 s, seeded by the agent id), `archetype` (P4-03), `landed` (P4-04); colour and brightness come from `look.ts` (P4-02). - **Keyboard and accessibility of the panel** (P5-04, `apps/web/src/panel/a11y.tsx`; audit, deferred items and the axe summary in `docs/tasks/notes/P5-04-a11y.md`). Reduced motion: one `prefers-reduced-motion` rule turns off every animation and transition under `.pnl`, each animating stylesheet carries its own block, and code-driven smooth scrolling (`scrollBehavior()`) jumps instead. ### 2.2 Backend: Node.js 22+ / TypeScript "Mission Control" server

**Recommendation:** Node.js (LTS) with TypeScript, Fastify for HTTP, `ws` for WebSockets, `better-sqlite3` for persistence (WAL mode), `zod` for shared schemas.

Why Node and not Rust/Python: the agent CLIs are all Node-friendly, the Claude Agent SDK is first-class in TypeScript, `node-pty` exists for wrapping arbitrary CLIs, and one language across server and UI lets you share the protocol types (`packages/protocol`). Bun is a reasonable substitute if you prefer it (`bun:sqlite`, fast startup), but `node-pty` and the SDK are better tested on Node.

Responsibilities:

- **Agent runtime**: spawn, supervise, pause, resume, restart and kill agent processes; own their stdio; enforce hard caps (§5.4).
- **Adapters** (see §3): translate each runtime's protocol into one internal event model. **The brains are agents too** and run through the same adapter (§5.1).
- **Status store**: the always-current, read-without-asking status of every agent (see §4) — a rebuildable projection of the event log, never the source of truth.
- **Domain model & persistence**: projects, tasks, bodies, workspaces/worktrees, proposals, questions, agent sessions, event log — in SQLite (§6).
- **Brain mailboxes**: the event-driven wake-up mechanism for the Harmonizer and Waykeepers (§5.2).
- **API**: WebSocket for live events with snapshot + resume (§6.3), plus a small REST surface for history. Authenticated with a single-user token (§8).
- **Process cleanup** (P4-14, SPEC decision 76; notes and the safety argument in `docs/tasks/notes/P4-14-process-cleanup.md`): a Steward's leftover processes — dev servers, watchers, headless browsers that outlive its work — are found by **attribution** (`runtime/process-attribution.ts`, pure) over a `ps` snapshot (`runtime/process-table.ts`: `ps -A -ww -o pid,ppid,pgid,uid,stat,lstart,command` on macOS and Linux; working directories from `/proc/<pid>/cwd` or `lsof -a -d cwd`; the agent marker from `/proc/<pid>/environ` or `ps -E -ww -o pid,command` — only what follows the known command line counts, and macOS hides the environment of platform binaries; listening ports from `lsof -iTCP -sTCP:LISTEN`, or `/proc/net/tcp` + `/proc/<pid>/fd` on Linux without lsof). **The marker:** the supervisor puts `GALACTIC_AGENT_ID=<agentId>` last in every agent child's allow-listed environment (no spec can override it), so everything an agent starts inherits it. A process of the server's user is the Steward's when, walking up its parents, the first deciding fact says so: a reaper (pid 1, `launchd`, `init`, `systemd`) or the server's own tree (itself, its ancestors, its process group) is nobody's; a member of a process group the supervisor started **in this server run** (`ProcessSupervisor.agentGroups()`: one per spawn, restart or resume, pgid = the CLI's pid, members started within the leader's lifetime as this run saw it — from the fork to the moment its `exit` fired, not after the drain and reap — never a PID-table row of an earlier run, whose pgid may since name the user's processes) is that agent's; a child of one of the Steward's is the Steward's (escaped with `setsid`); an orphan (parent a reaper), or a process below an orphan of the Steward's, whose identity (pid, start time) the server **remembered** is the Steward's (`why: remembered`, no marker needed): while a Steward's CLI runs, `StewardProcesses` records every process taken through its groups (by the two rules before) — on every list and stop and 750 ms after each `agent.tool_call`/`agent.idle` of the Steward, in memory for this server run, at most 2048 per Steward, forgotten once a snapshot no longer shows it — because Claude Code runs each Bash command in a process group of its own and macOS `ps -E` hides the environment of Apple binaries (`/bin/sh`, `/bin/zsh`), so a tool command's shell orphaned when the CLI died carries no readable marker; otherwise an orphan is the Steward's only when **all** of: the Steward has a task worktree (`…/.galactic/worktrees/<task>`), the orphan started inside one of the Steward's sessions (`agentSessions()`: each spawn or resume to its end, ±1 s for `lstart`, plus an earlier run's latest row of this boot to its recorded end — captured before this run's first spawn of the agent overwrites it, so a resumed Steward keeps it), its working directory is inside that worktree, and its environment carries the Steward's marker — an unreadable environment is no marker; below such an orphan every process needs the marker (or to be remembered) too; neither orphan rule ever takes a **user-facing app** — a command inside a macOS `*.app/Contents/` bundle (`code .` → Electron, terminal emulators) or a terminal multiplexer server (`tmux`, `screen`, `zellij`, `dtach`, `abduco`) — nor anything below one, because what the user later does in it (other folders, integrated terminals, panes) inherits the marker; anything else (a child of the user's shell, of the server, of another agent, a daemon the user started in the worktree) is not. `runtime/steward-processes.ts` (`StewardProcesses`, built by `composeRuntime` from `ComposeOptions.processes`, `index.ts` passes the supervisor) lists them — its own CLI left out while the Steward runs, and what that CLI uses (its direct children: MCP servers, the shell of a tool command, and their descendants) marked `held` — and stops them: every requested pid must be attributable now (else nothing is signalled, `DomainError('invalid')`); the attributed descendants go too, except held ones not named themselves; "stop all" (no pids) only for a Steward that ended; a target that started in the snapshot's own second is re-attributed after that second (and skipped if still that young); right before SIGTERM the table is read again and a pid whose start time or parent changed is skipped; nothing is signalled once the service is disposed (shutdown), checked after each wait; SIGTERM + SIGCONT to each pid (never a group), SIGKILL after `termMs` (3 s) to the ones whose pid *and* start time are unchanged; `agent.processes_stopped{agentId, pids, commands (clipped, redacted), forced?, by, sweep?}` is logged and `StopProcessesResponse.skipped` lists what was left alone. The **sweep** (a log subscriber) stops what is attributable when a Steward ends (`finished`/`failed`/`stopped`, after `whenExited` — the supervisor's own group reap — or 15 s) and, for every ended Steward of a task, when the task becomes `completed`/`failed`/`archived`; a live Steward is never swept (checked again right before the signals, against a resume), and neither is an interrupted one (shutdown: it comes back). Exposed as `GET /api/agents/:id/processes` and `POST /api/agents/:id/processes/stop {pids?}` (bearer-guarded; 404 unknown agent, 400 not a Steward, a pid that is not its, or no pids for a running Steward; the panel sends exactly the pids it showed after reading the list again) and as the brains' `list_steward_processes` / `stop_steward_processes` tools (§5.3). Residual risk: `lstart` has one-second resolution and the last identity read precedes the signal by a few milliseconds, so a pid recycled within that window *and* within the same second, with the same parent, is not detected; pid reuse on macOS and Linux cycles through the whole pid space first, so this needs a wrap-around inside that window. Further residual risks (notes): on macOS `ps -E` prints the environment space-separated, so a variable whose value contains ` GALACTIC_AGENT_ID=<this Steward's id>` — or an argv rewritten between the two `ps` reads to end that way — reads as a marker; a Steward that exports its own marker into the worktree's `.envrc`/`mise.toml` marks the user's later shells there once the user allows the file.
- **Settings** (P25-01, SPEC decision 51): `config/settings.ts` (`SettingsService`) reads the effective settings, validates a patch as a whole, writes `config.json` atomically (read fresh, changed keys merged, checked with `ConfigFile`, written to a 0600 temporary file and renamed — the token and every other key kept) and applies live what it can: the global default table (`setGlobalDefaultPolicy`), retention (`Archival.retentionMs`), caps (`CapsEnforcer.update`; running agents keep theirs) and the tier; the projects root and `stewardsLoadUserSettings` need a restart (`restartRequired`). An environment-decided setting (`envOverrides`: `GALACTIC_PROJECTS_ROOT`, `GALACTIC_RETENTION_DAYS`, any `GALACTIC_MAX_*` locks `caps`) is refused with 409 `env_override`. The projects root is saved cleaned (trimmed, `~` expanded, normalised) and refused with `Workspaces`' own rule (`unsafeFolder` on the `canonical`, symlink-free path: `/`, the home directory itself, inside or containing the data directory — `dataDir`, the config's and the database's folders).

### 2.3 Desktop shell: none required at first; Tauri 2 later if desired

Because the server runs as a normal local process and the UI is a web app, the simplest v1 is `galactic start` → opens `http://localhost:4321`. If you want a "real app" with a dock icon, tray status and auto-start, wrap the *same* web UI in **Tauri 2** (small binaries, Rust core, mobile targets exist). Electron is the fallback if you ever need Node inside the shell itself, but you don't: the server is already a separate process, and Electron's size/memory cost buys nothing here.

### 2.4 Mobile / remote access: PWA over Tailscale Serve

**Recommendation:** make the web UI a PWA (installable, offline shell, push notifications) and expose the local server privately with **Tailscale Serve** (`https://<machine>.<tailnet>.ts.net`).

- Tailscale gives you a private network between your computer and phone, valid HTTPS certificates (needed for PWA, service workers, and WebSockets on iOS), and identity-based access — with **no public port**. It is the option the tunnelling comparison recommends for private dashboards ([source](https://guides.happier.dev/cloudflare-tunnel-vs-tailscale-funnel-vs-ngrok-for-claude-code-codex-opencode)).
- If you ever need access from a device that cannot run Tailscale, switch to **Cloudflare Tunnel + Cloudflare Access** (SSO in front of the tunnel). Never expose the raw server on a public port: it can start processes on your machine.
- A native mobile app is *not* needed. If it ever is, Tauri 2 can build iOS/Android from the same web UI. The phone must degrade gracefully: lower quality tier, touch controls (one-finger orbit, pinch zoom, tap select), and a "list mode" for when 3D is too heavy.
- **Push notifications on iOS** work only for a PWA installed to the Home Screen, need a user gesture to request permission, and require the server to speak Web Push (VAPID keys, `web-push` library) to Apple's/Google's push service over the public internet. That is server-side work listed in Phase 7; treat push as best-effort. The service worker must use a versioned, network-first app-shell strategy and never cache API/WebSocket responses.

## 3. The agent adapter layer (mixed CLIs)

This is the most important design decision for a mixed-CLI setup. **Decision (SPEC.md §7, #5):** only Claude Code is implemented on day one, but the communication layer is a runtime-agnostic `AgentAdapter` interface with a fake adapter and a conformance suite, so adding Codex, Gemini CLI or PTY-wrapped CLIs later is one new adapter folder.

A session is owned by exactly **one** transport: an adapter cannot "complement" another adapter's session with a second protocol handle. Each runtime therefore has one adapter, chosen as follows.

### 3.1 Day one: the `claude-sdk` adapter (Claude Agent SDK, TypeScript)

**Stewards, Waykeepers and the Harmonizer all run through the [Claude Agent SDK](https://code.claude.com/docs/en/headless) adapter in v1.** The Harmonizer and Waykeepers already need the SDK for their custom tools, so this is one integration rather than two, and it gives the richest control: hooks, subagent trees (`parent_tool_use_id`), structured output, cost in the final `result`, and resume by session ID (`resume: <session_id>`).

Spawn options (per SPEC §3.5–3.6 and decision 17):

- **Subscription login, not `--bare`.** Bare mode skips CLAUDE.md, hooks, skills, MCP servers and plugins — precisely the repository context a Steward needs — and does not use the subscription login. `bare` is an opt-in per spawn for reproducibility experiments only.
- `cwd` = the Steward's **git worktree** (created by the server under the project's workspace; branch named after the task).
- Permission handling via the SDK's permission callback/hook, which asks the spawn's **permission gate** (below): allowed actions return immediately, denied ones are refused with the reason, everything else becomes `agent.needs_input(kind: "permission")` and blocks the tool call until the user answers.
- Clarification questions: the `AskUserQuestion` tool becomes `agent.needs_input(kind: "clarification")`.
- Graceful stop: `interrupt()` and wait for the turn to end before terminating (SIGTERM alone leaves an in-progress turn and any pending permission unanswered).

*Verified in Phase 1 (P1-08, `docs/tasks/notes/P1-08-sdk-spike.md`):* the SDK bundles its own Claude Code binary and reads the same login as the `claude` CLI, so in-process brains with custom tools run under the subscription; cost is reported per turn as a cumulative estimate (SPEC §8, both answered). What the spike fixed about the adapter's shape:

- **One long-lived `query()` per agent with streaming input.** The inbox (P1-07) is the `AsyncIterable` prompt; each delivered message ends in a `result` (→ `agent.idle`). `query.interrupt()` cancels the current turn only: that turn ends with an error result the adapter maps to `agent.idle`, and the next message runs in the same session. `sessionRef` is the SDK session id, assigned by the adapter (`sessionId`) and re-opened with `resume`.
- **Every tool call goes through the permission gate via a `PreToolUse` hook** (the `canUseTool` callback alone fires only for what Claude Code would prompt for itself). The hook calls `opts.gate.check(toolCall)` and answers `allow`/`deny` from its verdict and `ask` for the rest; `ask` lands in `canUseTool`, which opens `agent.needs_input(kind: permission)` and blocks until the answer. `AskUserQuestion` arrives in the same callback and is answered through `updatedInput.answers` → `agent.needs_input(kind: clarification)`.
- **The gate is the server's, not the adapter's (P1-18).** `SpawnOptions.gate: PermissionGate` — `check(toolCall) → {allow} | {deny, reason} | {ask, action?, reasons}` — is built per spawn by `runtime/permission-gate.ts` from the project's policy table (`domain/permissions.ts`, P1-10) and the agent's caps: the tool-call cap is checked first, and a call refused for the cap also trips it, so the agent is stopped rather than left retrying. Adapters never see the policy or the caps; the ACP adapter's `request_permission` and a PTY adapter's prompt detection call the same `check()`, so every runtime gets the same decisions from one implementation and the policy engine has one caller. The fake adapter runs every tool call through it too. A call the engine cannot classify (an opaque command, an unknown or MCP tool) is decided by the table's `unclassified` entry — `ask` unless the project is `trusted` (SPEC decision 49, §8 below); a push inside such a call still asks.
- **The supervisor spawns the CLI** through `spawnClaudeCodeProcess`, so the SDK session is a child in its own process group with a row in the PID table like any other runtime.
- **`bare` needs an API key** (no subscription login in bare mode); the option is refused without one.

Decided while implementing the adapter (P1-09, `apps/server/src/adapters/claude-sdk/`):

- **A job ends in `agent.idle`, not `agent.finished`.** An SDK session is long-lived: every turn's `result` becomes `agent.idle(cost)` and the session waits for the next message; the Waykeeper (Phase 2) closes the task and stops the agent. `agent.finished` is reserved for the CLI ending on its own (a clean exit, reported by the supervisor as `exited`), `agent.failed(crash)` for an unexpected exit and `agent.stopped` for a completed stop — one terminal event per session, mapped from the supervisor's `ProcessOutcome`. The conformance suite's `jobEnd: 'idle'` describes this.
- **`agent.tool_call` is emitted when the gate lets the call run** (from the `PreToolUse` hook, or from `canUseTool` after the user allowed it), never from the assistant's `tool_use` block, so a refused call is not counted against the tool-call cap and the transcript explains the refusal. Tool results come back as `agent.output(kind: tool)` excerpts; subagent output is prefixed `[subagent]`.
- **Pause is `SIGSTOP` on the process group, resume `SIGCONT`.** The turn in flight — model call, tool, shell children — freezes in place and continues afterwards, which is what the panel's pause means; cancelling the turn would lose work. `stop()` sends `SIGCONT` first, so a paused agent still stops gracefully (interrupt → turn end → SIGTERM → SIGKILL).
- **An error result that is not ours** (`error_max_turns`, an API failure) is a transcript line plus `agent.idle`, not a failure: the session is intact and the next message runs. The error result of our own `interrupt()` is just `agent.idle`.
- **Environment:** the CLI inherits the supervisor's allow-list plus `CLAUDE_PASS_ENV` (API routing and login variables: `ANTHROPIC_BASE_URL`, `CLAUDE_CODE_OAUTH_TOKEN`, Bedrock/Vertex settings, …) plus the adapter's own `env`; `ANTHROPIC_API_KEY` reaches a child only through that `env`, for `bare`. The session id is assigned by the adapter (`sessionId`), so a server that itself runs under Claude Code never leaks its own session id to its agents.
Decided in the phase review (P1-30, P1-32, P1-36, `docs/tasks/notes/P1-review.md`):

- **One gate check per tool use.** The `PreToolUse` hook's verdict is remembered by `tool_use_id`; `canUseTool` reuses it (asks the user for an `ask`, allows a hook `allow` without a second check), so a call is gated once and has one `agent.tool_call`. Both callbacks deny when the gate throws. `PermissionGate.check(call, {reserve?})` exists for adapters that must re-check without the cap pre-flight.
- **The query loop ending is a failure while the CLI lives.** If the iterator throws (also during an interrupt) or ends and the process is still running with no terminal event after 2 s, the adapter emits `agent.failed(runtime)` and stops the child.
- **Pause needs a process.** Pausing before the CLI exists is refused (the runtime reverts its own paused flag). `interrupt()` while paused sends `SIGCONT` and emits `agent.resumed` first (the runtime resumes first itself). Trade-off of `SIGSTOP`: the CLI's own tool and API timers keep counting while frozen, so a long pause can end the frozen call in a timeout.
- **Mapping:** a `result` with `is_error: true` (also with subtype `success`) is an errored turn — transcript line + `agent.idle`, like the other error results. `AskUserQuestion` with several questions asks them one by one (one `needs_input` each); a multi-select question says "separate the labels with commas" and passes the answer as typed. Cache read/creation tokens are added to `inputTokens` (the protocol `Cost` has one input count). `rate_limit_event` warnings/rejections during a turn become `agent.progress`. An init `session_id` that differs from the resumed ref is reported. Ended sessions are freed; events of a session replaced by a same-agent resume are dropped. An idle stop closes the input, so the CLI exits on stdin EOF before any signal.
- **Brains:** `role !== 'steward'` gets `settingSources: []` (no repository CLAUDE.md, hooks or skills), its `systemPrompt` as the whole prompt, and its `ToolDefinition`s as an in-process MCP server (`mcp__galactic__*`, JSON Schema converted to the zod shape the SDK wants). A Steward keeps the Claude Code preset and the repository's settings; a Steward `systemPrompt` is appended to the preset.

A brain's own tools (`SpawnOptions.tools`) are server code checked by `DomainCommands`: the permission gate allows them by name (bare or `mcp__galactic__<name>`) after the tool-call cap and never consults the policy table for them (P2-06).

**Symlinked workspaces (dev-machine run, 2026-10-02).** Claude Code resolves its cwd, so on a workspace reached through a symlink (macOS `/var` → `/private/var`, a symlinked projects folder) it names resolved paths. The engine stays lexical; the gate passes the resolved spellings of the workspace and the cwd as `PolicyContext.aliases` (`{from: resolved, to: given}`), and both path checks judge a path under `from` as the same path under `to`.

**Permission routing (P2-04).** The gate is the one place a permission is decided. Adapters call `check()` from their hooks; the runtime calls `decide()` (no cap reservation) on every `agent.needs_input(kind: permission)` that carries a tool call, before a question is opened: `allow` / `deny` answer the adapter and log `permission.decided{agentId, questionId?, toolCall (redacted), decision, action?, reason?, decidedBy: system}` with no question row; `ask` opens the user-held question. The gate reads the policy and the workspace on every check (the agent's project's `permissionPolicy` and `workspace`, else the global default and the spawn's; the spawn-time values only for agents outside any project) and logs its own hook refusals as `permission.decided{deny}` without `questionId` (cap refusals are the agent's failure). SPEC decision 31. `decide()` reserves no tool call, because the SDK and fake adapters' hooks already did: a future PTY or ACP adapter that asks the runtime directly, without a hook, must reserve in its permission path, or its allowed calls escape the tool-call cap.

### 3.2 Later: the ACP adapter for other runtimes

[ACP](https://blog.marcnuri.com/agent-client-protocol-acp-introduction) is "LSP for coding agents": JSON-RPC 2.0 over stdio, introduced by Zed in August 2025, adopted by JetBrains and others, with a registry launched in January 2026. Claude Code (`claude-agent-acp`), Codex (`codex-acp`) and Gemini CLI (`--acp`) all speak it, and by early 2026 25+ agents were compatible ([source](https://codex.danielvaughan.com/2026/06/10/agent-client-protocol-microsoft-intelligent-terminal-codex-cli-multi-agent-ide-ecosystem/)). When the second runtime arrives, GalacticAgents becomes an ACP *client*, like an editor, using the official TypeScript ACP SDK:

- `session/new`, `session/prompt`, `session/update` (streamed), `session/cancel` give spawn / talk / observe / stop with one code path; `session/load` (capability `loadSession`) is the resume path.
- **`session/request_permission` is tool authorization**, not a free-form question: map it to `agent.needs_input(kind: "permission")`.
- **Clarification questions arrive via form elicitation** (`elicitation/create`) and only if the client advertises `clientCapabilities.elicitation.form` in `initialize`; without it the agent's question tool is disabled. The adapter must advertise it and handle it → `agent.needs_input(kind: "clarification")`.
- A headless server should not advertise `fs/*` or `terminal/*` client methods unless it implements them faithfully. Document the exact capability set in the adapter README and have the fake ACP agent of the conformance suite assert on it.

*Verify before building:* what `claude-agent-acp` exposes for cost, `loadSession` and spawn options.

### 3.3 Fallback: PTY adapter for anything else

For CLIs with no machine protocol, spawn them under `node-pty`, stream the terminal to the UI (xterm.js in the side panel), and derive status heuristically (output activity, exit code, prompt detection). Treat this as "observable but dumb": no structured permission requests, so questions must be detected by regex/LLM and surfaced as best-effort. A PTY agent cannot be resumed after a restart; it is shown as `interrupted` with a "restart task" action.

### 3.4 One internal event model

Every adapter emits the same normalised events (schemas in `packages/protocol`) into the server's event bus:

`agent.spawned · agent.output(text/tool/thinking) · agent.tool_call · agent.needs_input(questionId, kind, question: QuestionContext{text, options?, toolCall?, permissionAction?}) · agent.progress(summary) · agent.idle · agent.stalled · agent.paused · agent.resumed · agent.finished(result, cost) · agent.failed(error) · agent.stopped`

The `AgentAdapter` interface: `spawn(opts)`, `send(sessionId, message, {interrupt?})` (starts a turn now — the server's per-agent inbox is what waits for idle, so adapters keep no queue and may reject a mid-turn message; P1-19), `answer(questionId, answer)`, `interrupt`, `pause`, `resume`, `stop`, `resumeSession?(sessionRef)`, plus the `events` stream. `spawn(opts)` accepts `tools` and `systemPrompt` so the same adapter runs the brains, and `gate` (§3.1) for its tool calls. An adapter is a translator, not a scheduler: the runtime owns the inbox, the caps, the permission policy and the event log.

The UI, the status store and the supervisor brains only ever see these events. Adding a new runtime means adding one adapter, nothing else — including for the brains, which never import a runtime module directly.

Two refinements decided while building the fake adapter and the supervisor (P1-01, P1-03):

- **`agent.spawned` is emitted by the server's runtime layer**, not by adapters, when `spawn()` / `resumeSession()` resolves: it carries the body, supervisor, task and project ids the adapter never sees, plus the `sessionRef` from the handle — written to the agent row in the same transaction (P1-21). **Every other `agent.*` event comes from the adapter, the one emitter for its session** (P1-20). The process supervisor tells the adapter what only it can know as a `ProcessOutcome` through the spec's `onOutcome` hook — `start_failed`, `crashed`, `exited` (clean, or announced with `expectExit()`), `stopped{by}`, `restarting` — and the adapter decides the verdict (`agent.failed(reason: runtime)`, `agent.failed(reason: crash)`, `agent.stopped`, or `agent.finished` from the runtime's own final message), so a process exit and a final result can never race each other into the log.
- **One terminal event per agent (P1-17).** The runtime logs exactly one of `agent.finished` / `agent.failed` / `agent.stopped`: a cap stop is flagged on the live entry and the adapter's `agent.stopped` is folded into `agent.failed(reason: cap)` whichever arrives first; a straggler from an ended agent is dropped; an event for an agent the runtime never spawned is reported and never logged. The status store treats an ended record as a sink.
- **`agent.needs_input` opens the question (P1-23).** The runtime inserts the `Question` row and emits `question.opened` in the same command as the event; `answer()` closes the row and emits `question.answered` with the bumped `version`. The server owns questions (§5.3); holder routing arrives with Phase 2.
- **`agent.created{agent}` describes the row** (emitted by whichever command inserts it: the Phase 1 runtime, the Phase 2 `spawnAgent` command), so a replaying client builds the same `agents` table as a snapshotting one (§6.2); `agent.spawned` then reports the session. `agent.idle` may carry the running `cost` for runtimes that meter per turn.
- **Adapters emit `agent.output` per content block, never per token**: one transcript row per token is not a transcript. The pipeline's redaction (§6.2, §8) is boundary-aware since P1-27, so a key split across two deltas no longer leaks — but the per-block rule stands for the sake of the rows. The runtime redacts every string in the other agent events too (tool inputs, question text, results, errors, progress summaries) before they reach the log.
- **`agent.paused` / `agent.resumed` / `agent.stopped` emitted by an adapter carry `by: {type: system}`**: the adapter interface has no actor. Who asked is recorded by the matching `control.*` event the runtime appends first (decision 11b), so the log always has both.

**Restart recovery (P1-14, P1-15, P1-29, P1-32, P1-33; SPEC decisions 8, 21, 23).** `agent.interrupted{agentId, reason, pending?}` is the runtime's event for a session the server lost without the agent ending. A graceful shutdown first logs every live agent's fate — `agent.interrupted{pending}`, or the `agent.stopped{by}` / `agent.failed(cap)` a stop already under way was heading for — then flushes the transcripts, then stops all processes in parallel (the server's hard deadline is grace + term + 10 s). A start after a crash of the server logs `agent.interrupted` for every agent whose last state is still live, or `agent.stopped` when a `control.stop` after its last spawn was never answered. The status store folds `interrupted` to an ended state that only a new `agent.spawned` leaves. `AgentRuntime.recover()` reads the log once and reopens every interrupted agent through `recoverAgent(id)` — the same path the panel's "Resume session" (`POST /api/agents/:id/recover`) takes: refused unless the agent is `interrupted` and not live; the permission policy, workspace, prompt and `bare` come from `Agent.meta` (until tasks carry them in Phase 2); every `message.sent` without a `message.delivered` is queued again with its original id, so a second restart before delivery still knows it is pending and a crash mid-turn does not deliver the turn's message twice. A failed resume logs `agent.interrupted{reason: "resume failed: …"}`. An agent recovery leaves interrupted for the user (passed over, not resumable, or a resume that failed for good) also gets `recovery.needs_attention{agentId, reason}`, once per interruption (P25-01; the notification feed's "work interrupted by a restart").

**Message and question lifecycle (P1-33, P1-34).** `message.delivered{messageId, agentId}` is logged when the adapter's `send()` resolved; a refused delivery waits at the head of the inbox and is retried at the next idle (three attempts). A delivery marks the agent busy at once, so a pause/resume or a second message right after cannot reach a mid-turn session. An agent's open questions are cancelled (`question.cancelled{questionId, agentId, reason, version}`, row status `cancelled`) in the same command as its terminal or interrupted event, and when it goes idle with a question still open (an interrupt withdrew it); a late answer is refused. A stop whose adapter call throws ends the agent with `agent.failed(runtime)`; a stop that resolved without an adapter event ends with the runtime's `agent.stopped{by}` — an agent can always be stopped. A message sent while a stop is under way is refused before it is logged. A cap hit before the session handle exists is acted on when it arrives.

The **process supervisor** (`apps/server/src/runtime/supervisor.ts`) is the one place that spawns and kills child processes: each in its own process group (killed by group, corner case 4), stdio captured, an allow-listed environment (§8), restart policy off by default, and one graceful stop sequence — the runtime's interrupt hook (SIGINT to the group by default) → wait for the turn to end with a timeout → SIGTERM → SIGKILL (corner case 8b). Its PID table is the `agent_processes` table (migration 0003): runtime bookkeeping that never appears in a snapshot and has no events. On startup `reconcile()` treats every `running` row as a previous server life: a still-running orphan is killed by group (nothing can re-attach to a live process, corner case 3), and both dead and orphaned rows become `interrupted` for the resume path (P1-14) to respawn from `agents.sessionRef`. Since the phase review (P1-32, P1-37): the interrupt hook runs inside the grace window (a CLI that never answers the interrupt still reaches SIGTERM/SIGKILL); **whenever a group leader exits, for any reason, the rest of its group gets SIGTERM (and SIGCONT) then SIGKILL**, so dev servers and background shells do not outlive their agent, and `reconcile()` also kills the leftover group of a dead leader recorded in this boot; process identity is the basename of the whole `ps -o comm=` (macOS paths with spaces) plus a start-time check (`ps -o lstart=`, 5 s tolerance) against the row's `startedAt`, so a recycled pid — say the user's own `claude` — is never killed; `adopt()` refuses a restart policy (the SDK could not reconnect to a relaunched CLI).

## 4. Supervision without interruption (status store)

The spec's requirement — supervisors know statuses without interrupting — is solved by **never asking the agent**. Instead:

1. Each adapter's event stream is folded into a per-agent **status record**: `state ∈ {starting, working, waiting_for_input, idle, stalled, paused, interrupted, finished, failed, stopped}`, `current_activity` (last tool call or a rolling LLM-written one-liner), `last_event_at`, `pending_question`, `progress` (task-level checklist if the agent reports one), `cost_so_far`, `caps` (used vs. limit). `stalled` is set by a per-runtime silence threshold, never by killing.
2. The status store is an in-memory **projection** of the event log, rebuildable from it on startup and pushed to the UI over WebSocket as batched diffs (≈10 Hz, never per token, and only for records that changed: the record carries `startedAt` and the client extrapolates the running wall clock from it rather than being sent a fresh `caps.wallClockMs.used` every second — P1-25). **The projection has one implementation, in the server** (P1-05): clients receive status records in the `snapshot` and as status messages afterwards and never fold `agent.*` events into records themselves — a second implementation in the web client would drift from the server's and make a resuming client disagree with a snapshotting one (decided with P0-18).
   Ended records are retained for a bounded time and count (default 24 h, 500) and then dropped; the drop is announced in the next `status` message (`removed`) so clients forget them too, and the log keeps the history (P1-16). After a replay the full set is sent with `replace: true` and the client swaps its map, so a record pruned while it was away disappears too (P1-38). `pendingQuestionId` is cleared by `question.cancelled`, `agent.idle` and `agent.interrupted` (P1-34).
3. The Harmonizer and Waykeepers get a `get_agent_status(agent_id)` / `list_supervised_agents()` **tool** that reads the store. Reading it costs nothing to the supervised agent.
4. Task and project states (SPEC §4.4) are derived in the server from agent states and open questions — no LLM call needed for the basic status views.
5. Optional cheap summariser: every N events (or on idle), a small model turns the recent event window into a human sentence ("Refactoring auth module, 3 files edited, running tests"). This drives both the panel text and the satellite animation choice (gathering / transporting / building). The raw last event is always shown next to the summary so a lying summary is visible.

---

The system summary counts (open questions, user-held questions, blocked tasks and projects) come from a pure function in `packages/protocol` (`summarize`, P2-15) over the domain rows: server and client compute them from the same state, so no summary message is sent and it cannot drift.

**Status views (P5-02).** The panel answers "the status of anything" (SPEC §4.3) without an LLM call: `apps/web/src/panel/status/status-model.ts` computes the system view (projects and tasks by work state, agents by state, a "needs attention" list — blocked on the user, failed, interrupted, stalled, close to a cap, in that order, oldest first within each — open questions by kind and holder, decision 58's waiting count, cost totals with the Harmonizer's own cost — P5-05: every other agent shows its own on its card, the Steward view or its project's view — and the global caps' usage), the project view (its tasks blocked first with each task's Steward state and summed cost, Stewards against `maxStewardsPerWaykeeper`, its questions, cost and sub-projects) and the task facts the Steward view adds, all as pure functions over the client world (folded log + status records) and the settings' caps. Costs sum `costSoFar` over the status records the server still holds (live, or ended within the 24 h / 500 retention), dollars where reported and tokens only for agents without dollars, and every cost fact says so; "agents active today (lifetime cost)" is the whole `costSoFar` of the records whose last event is after local midnight (a record has no per-day split). The system view leaves the scene harness's agents (`meta.harness`) out of attention, costs, agent counts and caps, and takes the Harmonizer from `currentHarmonizer`; a blocked task whose project is blocked folds into the project's attention entry ("· N blocked tasks"). Two counts are estimates: the per-Waykeeper cap meter counts the project's tasks' live Stewards (the enforcer counts by `supervisorId`), and spawns in the last hour come from the agents' `createdAt` (the enforcer keeps its own in-memory window) — their tooltips say so. The dock's "Chat | Status" switch (Harmonizer and Waykeepers, and the Harmonizer slot with no Harmonizer row, decision 44) is a per-browser preference (`galactic.panel.dock.view`); the conversation stays mounted under the status view. The only LLM path is the optional "Ask the Harmonizer for a narrative status" button, an ordinary chat message to the Harmonizer (which answers with `report_status`).

**Hierarchy resume (P2-16).** The composition registers the brain definitions (`defineBrains`) before `recover()`. `AgentRuntime.recover()` interrupts the live agents deepest first, then reopens the interrupted ones shallowest first; an agent whose role has a definition goes through the brain resumer (`BrainRunner.resume`), any other through `reopen` (`resumeSession(sessionRef)` with `RESUME_PROMPT`, falling back with `freshPrompt` to `adapter.spawn` on the same row). A brain's mailbox is rebuilt from the log (`brains/requeue.ts`): everything after its last delivered turn, minus its own effects and messages it already got. The reopen records how far its first prompt folded the log on `agent.spawned.foldedUpTo`; a later requeue cuts there once that session's first turn ended (`agent.idle`), so a second crash folds nothing twice and a session lost before its first turn folds its items again. Inside the brain's own turn an actor-less event is dropped as possibly its own effect, except another agent's `agent.*` lifecycle, a question event or a proposal decision not in the same command (one `at`) as an event the brain is the actor of. The runner marks the folded messages delivered when the first turn ends, not when the handle comes back. **A resume can fail late:** the SDK adapter returns the handle at once and a lost or corrupt session shows only as `agent.failed` / `agent.finished` when the CLI exits. A session resumed from its ref that ends before its first `agent.idle` (and was not being stopped) is therefore a failed resume: it is logged `agent.interrupted{resume failed: …}` and a brain gets the fresh session on the same row (`ReopenOptions.onFallback` tells its runner first); a plain agent that failed before doing anything stays interrupted. `endAgentQuestions(…, 'interrupted')` keeps a brain's command-sourced questions (`meta.source: command`) open, and the ones of that kind an interrupted holder holds stay with it; recovery re-routes what an agent it passed over or could not resume held. `refuseReopen` also refuses a second Steward per task and a second Waykeeper per project. While `recover()` reopens, the interrupted agents it is about to reopen (and a brain whose lost resume is being replaced) are reserved (`AgentRuntime.isReserved`): the brain queries report them `starting`, so the spawn guards of a supervisor resumed first do not replace them, and question routing counts them living. `composed.keepHarmonizer(start)`, armed by `index.ts` after the boot-time start, replaces a Harmonizer that ends (other than by the user's `control.stop`) when none runs or is reserved, at most 3 times in 10 minutes. The Harmonizer's start notes also withdraw the open `ask_user` / `ask_confirmation` questions of an ended Harmonizer and name them (their answer would wake only the asker, and `finished_work` accepts only its own confirmation). `POST /api/agents/:id/recover` takes the same path; one Harmonizer at a time holds on both. After recovery and `startHarmonizer`, `announceRecovery` adds the report line to the running Harmonizer (`BrainRunner.note`); `BrainDefinition.startNotes(ctx)` gives lines for a session's first turn (the Harmonizer's unrelayed closure requests). A tool call in a brain's first turn waits for its agent id. A resumed session's first message is `RESUME_PROMPT`, plus — when the interruption cancelled questions of the agent (decision 21) — one line per cancelled question and "ask it again" (`AgentRuntime.resumePromptFor`); without it real Claude went idle. Steward sessions load `['user', 'project', 'local']` settings (`ClaudeSdkAdapter.stewardSettingSources`; the real-Claude checks use `['project', 'local']`), brains none.

**Restarting the Harmonizer (P5-06; SPEC decision 82).** `POST /api/harmonizer/restart` (bearer-guarded like every `/api` route; any authenticated client may call it, like `POST /api/agents/:id/stop` and the panel's controls — a control action, not a settings write, so not local-only) runs `harmonizerRestarter` (`apps/server/src/brains/harmonizer/restart.ts`), wired in `index.ts`, under the Harmonizer lock (`withHarmonizerLock`: one start of the Harmonizer at a time per runtime, shared by the boot start, `keepHarmonizer` and the restart, so one Harmonizer is structural). The live Harmonizer is stopped first, with `by: user`, and nothing else happens unless it ended — a stop that fails leaves it running and driven by its runner (500). The stop ends the open `ask_user` / `ask_confirmation` questions it asked (`meta.source: command`, kind clarification, not a project's closure question; one still open is withdrawn as the user) and the new one is told about them; the stop is the user's, so `keepHarmonizer` does not start another one beside it (its closure question is cancelled with the stop and `closureNotes` relays the closure request again; the questions it held move on as on any stop, P2-03), and a fresh one starts on the same runtime and working directory — the stopped one's, else the newest Harmonizer row's (one the user stopped from the ops console, an interrupted or failed one), else the boot setting (`GALACTIC_HARMONIZER`); with none of these it refuses. `StartHarmonizerOptions.notes` puts lines first in the new one's first turn, once: "the user restarted the Harmonizer from the panel … tell the user in one line", then one line per withdrawn question ("ask again if it still matters"), then its usual start notes. A start that fails after the stop is retried once on the boot runtime (what `keepHarmonizer` would start), logged through `onError`, so the user is not left without a Harmonizer. When the last Harmonizer is interrupted (not live), the fresh one starts beside its row: its own tool-asked questions are withdrawn by the new one's start notes, and the questions it *held* (a Waykeeper's, escalated) move on to the user once the new one runs (`AgentRuntime.releaseInterruptedHarmonizers`, called by every `startHarmonizer` that starts one, so `keepHarmonizer` too; decision 45). The row stays `interrupted` (an ended status is a sink), like the Harmonizers startup recovery passes over, and is not reopened while the new one runs. **Restart window:** at most 3 restarts per 10 minutes (as `keepHarmonizer`'s); past it the reply is 429 with `Retry-After` and "try again in N min". A Harmonizer's spawn does not count toward the per-hour spawn window (`CapsEnforcer.noteSpawn` skips the role; decision 43), so restarts never block Steward or Waykeeper spawns. The reply is `RestartHarmonizerResponse {agentId, replaced?}`; a second restart while one is under way, an interrupted Harmonizer on its way back (`runtime.isReserved`), a missing runtime or a refused start answer 409 `refused` (redacted); anything unexpected is 500. The scene harness's dormant stand-in is never taken for the Harmonizer. In the panel the Harmonizer's dock bar has `HarmonizerControls` (`apps/web/src/panel/controls.tsx`): Pause / Resume through `POST /api/control` on the agent, "Resume session" (`POST /api/agents/:id/recover`) only while it is interrupted, and "Restart Harmonizer" behind `ConfirmBox` (the shared inline confirmation, focus on "Keep"); no Stop. The dock stays on the `harmonizer` selection, which resolves to the newest running Harmonizer (`currentHarmonizer`), so it follows the new id when the stream brings it.

## 5. The Harmonizer and Waykeepers as "tool-armed" agents

Do not make the hierarchy purely prompt-based. Build the Harmonizer and Waykeepers on the Claude Agent SDK with custom tools that mutate the domain model, so the important decisions are auditable and the UI reflects them immediately.

### 5.1 Brains are agents, run through the adapter

The Harmonizer and each Waykeeper are rows in the `Agent` table (`role`, `runtime: claude-sdk`, `sessionRef`, `supervisorId`, `bodyId`) and are spawned through the **same `claude-sdk` adapter** as Stewards, with `tools` and `systemPrompt` supplied. Consequently they emit `agent.*` events, appear in the status store with real statuses and cost, have a satellite/HQ presence on their body, and are resumed after a restart like any other agent. `packages/brains` (or `apps/server/src/brains`) contains only prompts, tool schemas and tool handlers written against a `DomainCommands` interface — never SDK or runtime imports. The implementation is `Commands` (`apps/server/src/domain/commands.ts`, P2-01), built by `composeRuntime`: domain commands run synchronously under the one write rule and refuse with a `DomainError{code: not_found | invalid_transition | conflict | stale | invalid}` that rolls everything back; agent commands (spawn, stop, pause, resume, answering a question a live session asked) go through the runtime. Task and project state transitions follow one table (`domain/states.ts`, SPEC §4.4).

### 5.2 Mailbox, one turn at a time

Brains are long-lived but **event-driven, never polling**:

- Each brain has a **mailbox**. Wake-worthy events are appended to it: a user message, `question.opened / answered`, `proposal.decided`, `agent.finished / failed / stalled`, task/project control actions from the panel, a subordinate's report. Never `agent.output` or `agent.tool_call`.
- **One turn at a time per brain.** A turn drains the whole mailbox into a single prompt ("since your last turn: Steward S3 finished task T7; the user answered Q12; the user paused T9"). Events arriving during a turn wait for the next one. Two Stewards finishing together produce one turn, not two, and a brain's own tool side effects never re-enter it mid-turn.
- **Tools that need the user are non-blocking.** `ask_user`, `escalate`, `propose`, `request_project_closure` create the corresponding object and end the turn; the answer arrives later as a mailbox event. A brain's turn is therefore always short, and a restart never loses an hours-long in-flight turn.
- **The database is the brain's memory.** Each turn is seeded with the current state it needs (`list_supervised_agents()`, its project's tasks and open questions) rather than relying on an ever-growing transcript; sessions are reset periodically (e.g. on each project milestone) with a summary carried over, so context never silently compacts away "knows the status of every task".

**Brain runner (P2-06).** `apps/server/src/brains/runner.ts` drives one brain: it spawns it through `DomainCommands.spawnAgent` with `tools` and `systemPrompt` and calls `AgentRuntime.attachMailbox`; from then on messages to the brain (the user's chat, a subordinate's report) are only logged as `message.sent`, folded into the next turn by the mailbox and marked `message.delivered` once that turn is delivered. A turn starts only when the brain is idle and ends at its `agent.idle`; its prompt is "Since your last turn: 1. … 2. …" plus the seed block (supervised agents with status, the project's tasks, the open clarifications it holds or its agents asked). Events committed together become one turn. The whitelist is one table, `WAKE_RULES` (`brains/wake.ts`): `message.sent` from the user or an agent below the brain (`WakeScope.below`: a direct report, or a sub-project's Waykeeper asking the Harmonizer for closure); `task.created` in a Waykeeper's project by someone else (not `proposed`: plan tasks wait for their card); `question.opened/escalated/reassigned` to the brain as new holder and `question.answered/cancelled` naming it in `holders` (clarifications only; a question opened `toUser` concerns no supervisor); `proposal.*` decisions on proposals it owns; `agent.finished/failed/stalled` of supervised agents; `control.*` aimed at the brain, a supervised agent, a task or project it runs, or concerning it as a supervisor (`concernedSupervisors`, P2-14: an agent target concerns its supervisor; a task its Stewards' supervisors and its project's Waykeeper, or the Harmonizer for a standalone task; a project its Waykeeper(s) and their supervisors, the parent project's Waykeeper and the Harmonizer; never the actor). Tool handlers receive a `DomainCommands` proxy: every event a tool call appended is taken out of the mailbox, so a brain's own actions never wake it. `ask_user`, `escalate`, `propose`, `request_project_closure` (or any tool marked `endsTurn`) end the turn: later tool calls in it are refused with `turn_ended`; a refused command reaches the model as `{error: <DomainError code>, message}`. Session reset (after N turns, or on demand) has the brain call `carry_summary`, then `AgentRuntime.renewSession` replaces the adapter session on the **same agent row** (`agent.interrupted{reason: "session reset"}` then `agent.spawned`), and the new session's first prompt carries the summary. A reset keeps the questions the brain holds (the agent lives on; only its own open questions are cancelled with the old session). A tool call's events, as the command surface returns them, are only what that call caused — its own transaction and its agent effects carrying its actor — so another actor's event logged meanwhile still wakes the brain. The mailbox is in memory; P2-16 restores it after a restart.

**Placement (P2-20).** `checkPlacement` (`domain/agents.ts`) holds the hierarchy rules for `spawnAgent` and `updateAgent` (SPEC decision 32): the Harmonizer on Earth, one at a time, unsupervised; every other agent under its prescribed supervisor, matched by role and project. The Phase 1 ops console (`/api/agents` → `AgentRuntime.spawn`) is outside these rules. A brain is also woken when a clarification it asked through a tool (the Harmonizer's `ask_user`, a Waykeeper's own question — marked `meta.source: "command"` by the command surface) is answered or cancelled; a question its own session raised, and any permission question, is answered through the adapter and never enters its mailbox.

**Brain tests (P2-07).** Brains are tested without Claude through `apps/server/src/brains/testing/`: a `BrainScript` stands in for the model — turn rules match the turn prompt and their async bodies call the brain's real tools (through the runner, the gate and `DomainCommands`), chaining results; a `BrainTranscript` records every prompt, call, result and refusal, and `verify()` fails on an expected turn that never came, an unexpected turn or a refused call. The fake adapter's `script` step is the only seam.

## 6. Persistence, event log and API protocol

### 6.1 One write rule

Every command (a brain tool, a panel action, an adapter event fold) performs its **domain mutation and its event insert in one `better-sqlite3` transaction**; the event ID is the `events` rowid (monotonic, server-assigned); in-memory subscribers are notified **after commit**, strictly in `seq` order even when a subscriber runs a command of its own while being notified (its events are committed at once and published after the current batch). Events are buffered per outermost command and published only when it commits: a nested command that succeeded inside an outer one that then threw is rolled back with it and never published (P1-35). A crash can therefore never leave the domain tables and the event log disagreeing. **A command reads the clock once** (P2-01): every event it appends carries that reading as `at`, and every row it writes uses it for `createdAt` / `updatedAt`, so a client that folds `updatedAt = at` holds exactly the server's rows. Clients never trust their own timestamps for ordering. A migration that rebuilds a table (SQLite's only way to change a constraint) declares `-- migrate: foreign_keys=off`; the runner disables foreign keys around its transaction and refuses to commit if `foreign_key_check` reports anything (P2-02, migration 0005).

### 6.2 Two streams

- `events` — domain, status, question, proposal and lifecycle events, `message.sent` (what the user, a supervisor or the system sent to an agent — logged before it is queued, so a restart re-delivers what was pending and a brain's mailbox is fed from the log; P1-22) and `message.delivered` (the adapter accepted it; P1-33): small, ID-ordered, resumable, retained for a long time. This is the log that corner case 33 ("reconstruct any state") and the timeline scrubber replay.
- `transcript_chunks(agentId, seq, chunk)` — agent output (text, tool calls, thinking), written in batches (≈10 Hz), pruned by retention policy, redacted for known secret patterns **before** persisting and before sending to the UI. Redaction is boundary-aware (P1-27): the previous chunk's tail is matched together with the new text, a secret's head moves into the new chunk, and the newest chunk of an agent is held for 250 ms so a key split over streamed deltas is caught whole. Since the phase review (P1-31): the pipeline receives the **raw** output and redacts it itself (a chunk redacted on its own loses the context a split key needs); only consecutive chunks of the same kind are joined; after a gap longer than the hold, a key's head is kept only if it was safe on its own and the rest is masked; a private-key block is masked from its `BEGIN … PRIVATE KEY` line to its `END` line whatever the chunking (per-agent state, 16 KB cap); a subscribe backlog holds persisted rows only and subscribers are notified after the write succeeded; `prune()` never deletes an agent's newest row, so `seq` keeps increasing across restarts without a stored high-water mark (a Phase 8 "delete an agent's transcript" needs one).

The status store (§4) and the task/project states are projections over `events`; they are rebuilt on startup and never written back as truth.

**Work states (P2-15).** `WorkStateDeriver` (`runtime/work-state-deriver.ts`) is a log subscriber placed after the status store. Once every event of a commit is folded, it recomputes the tasks and projects the commit concerns with an ordered rule table (`domain/work-states.ts`, SPEC §4.4) and writes any difference through `setTaskState` / `setProjectState` as `*.state_changed` **without `by`**, so clients receive derived states as ordinary row changes and the conformance test still holds. It derives per commit, not per event: a command that sets a task and its project explicitly (a cancel) has both holds recorded before either is re-derived. A task's change re-triggers only its project, a project's change nothing. On restart it rebuilds its tables from the log without writing, then corrects only rows a crash left stale.

**Bodies (P2-02).** The catalogue is seeded by migration 0005 (`domain/catalogue.ts`: `freePlanets`, `freeMoons`, `chooseBody` with decision 25's preferences, returning the occupied planets when none is free; seeded asteroid generator `b-asteroid-n`). The "moved to …" marker is a first-class `Body.movedTo{bodyId, host, at}` column: `body.moved` writes it with the event's `at` (with `intoProjectId` when a standalone task joins a project's body, whose host is unchanged), `body.freed` clears it, and both sides fold it alike. `sweepMarkers(retentionMs)` frees markers by the log's clock (default 7 days until P2-13 reads the setting).

**Patch rule (P2-20).** `project.updated` / `task.updated` carry `changes` validated by `ProjectChanges` / `TaskChanges` (`packages/protocol`): absent or `undefined` is unchanged, an explicit `null` removes the field — allowed only on `CLEARABLE_PROJECT_FIELDS` (`repoPath`, `parentProjectId`, `permissionPolicy`) and `CLEARABLE_TASK_FIELDS` (`worktreePath`, `branch`), refused elsewhere. The commands and the web reducer apply changes with the same `applyChanges`, so a cleared key is absent on both sides, never stored as `null`; clearing an absent field emits nothing. `agent.updated` has no clearable fields.

**Retention (P2-13).** The retention clock is derived from the event log, not stored: for a project or standalone task it is the later of its last `*.state_changed` into `completed`/`failed` from a non-finished state and its last `*.updated{pinned: false}`, falling back to `updatedAt` for a row created finished or a pruned log (`domain/retention.ts`: `retained`, `sweepRetention`). `runtime/archival.ts` runs it hourly from the composition (once at start; injectable timers; off in tests), archiving with the ordinary `archiveProject` / `archiveTask` by `{type: 'system'}`, so there is no new event and no client fold. The period is `config.retentionMs` (`retentionDays`, `GALACTIC_RETENTION_DAYS`, default 7). A stored `retained_since` would be needed once events are pruned, or for a client countdown.

Two consequences for the client, decided with P0-18:

- **Domain state is derived twice by design** — the server's commands mutate the tables, the web client's reducer folds the same events — so the two must agree or a resuming client and a snapshotting one would show different worlds. Every command therefore emits events that fully describe its mutation (`body.created` for a new body, `project.created` with the whole project, …), and a **conformance test** (`apps/web/src/state/conformance.test.ts`, P2-01) drives the real commands and runtime through every domain event type and checks that replaying the recorded log through the client reducer equals the server's snapshot after every commit. Status records are exempt: they are server-owned (§4). A row's placement in the hierarchy changes with `agent.updated{changes: supervisorId | bodyId | taskId | projectId}`.
- **The per-project `PermissionPolicy`** (SPEC §3.6, decision 7) is stored in a `permission_policy` JSON column on `projects` (validated by the protocol schema; absent = default policy), added by migration with P2-01 and exposed as `Project.permissionPolicy?`. It is never parked in `meta`. The same migration (0004) adds `pinned` to projects and tasks (decision 11b).

### 6.3 WebSocket protocol (defined in Phase 0, used by every client from Phase 1)

1. Client opens the socket and sends `hello{token, lastEventId?, logId?}` as the **first frame** (browsers cannot set headers on a WebSocket upgrade). `logId` is the identity of the log its state came from.
2. Server replies with `snapshot{logId, seq, agents, bodies, projects, tasks, questions, proposals, statuses}` when `lastEventId` is absent, `logId` is not this log's (database deleted or replaced), or `lastEventId` is too old to replay; otherwise with the `events` since `lastEventId` followed by `caught_up{seq}`. Both `snapshot` and `caught_up` carry an optional `serverTime` (the server's clock when sent): the client keeps its offset to it, so anything that asks "how old is this event?" (event toasts) uses the server's clock, not the page's (P4-06 review).
3. Thereafter a single ordered stream of `{seq, event}`; the client derives all state from it and remembers `seq` + `logId` for the next reconnect. `seq` is never reused (`AUTOINCREMENT`). Transcript chunks are a separate, subscribable stream per agent.
4. The derived state lives in memory only. A client that has no state (a fresh page load) sends no `lastEventId` and takes a snapshot; resuming from a persisted `seq` onto an empty world would replay only the tail (P0-12). Persisting the world together with its `seq` + `logId` is possible later (a phone PWA), never `seq` alone.

Two more message kinds ride on the same socket (P1-05, P1-06): `status{statuses}` carries the status store's batched diffs (≈10 Hz; each record replaces the client's copy for that agent) and follows a replay's `caught_up` with the full current set, since records cannot be derived from the replayed events; `transcript.subscribe{agentId, since?}` / `transcript.unsubscribe{agentId}` open and close the per-agent transcript stream, whose `transcript{agentId, chunks}` batches arrive in per-agent `seq` order (history after `since` first, then live). A client that reconnects re-subscribes with the last `seq` it has. A socket too slow for any of the three streams is cut and resumes on reconnect.

**Chat history (P2-18).** The console's chat boxes fold `message.sent` from the stream into a per-agent list beside the folded world, not in it (the snapshot carries no messages and the conformance test compares the tables only); after a reload or a snapshot catch-up (the store counts snapshots; a chat box refetches when the count changes) the page backfills from `GET /api/agents/:id/messages` (the log's last 200 `message.sent` of that agent, an indexed read on `events(type, json_extract(payload, '$.agentId'))`, migration 0006), deduplicated by `messageId`. The route returns the text as the stream carries it: user-written text is not redacted (§8), and a Steward's report was redacted when it was made. The promotion flow's start-time scans of the whole log stay (once per boot). The other REST surface the console uses: `POST /api/proposals/:id/decide` (approve / edit / reject / park), `POST /api/questions/:id/answer` with the question's `version` (409 `stale`, "already answered by …"), `POST /api/control`, `POST /api/agents/:id/send`, `GET /api/runtimes`.

**Panel endpoints (P25-01).** All in `http/panel-routes.ts`, typed in `packages/protocol/src/panel.ts`, bearer-guarded:

- `GET /api/agents/:id/conversation?before=&after=&limit=`: `message.sent` to the agent merged with its `text` transcript chunks by (`at`, messages first, `id` / `seq`), paged by an opaque cursor (`<at>~m<id>` / `<at>~r<seq>`) in both directions, newest page by default; entry ids `m:<messageId>` / `r:<agentId>:<seq>` match the stream for dedup. Each source is read through a partial index of migration 0007 — `events(json_extract(payload,'$.agentId'), at) WHERE type = 'message.sent'` and `transcript_chunks(agent_id, at, seq) WHERE json_valid(chunk) AND json_extract(chunk,'$.kind') = 'text'` — with row-value cursor bounds, so a page reads only its rows (no sort of the agent's history, no JSON parse of every chunk). `lastSeq` is the newest *persisted* chunk when the page was read: `transcript.subscribe{since: lastSeq}` continues it and delivers a reply that was still buffered.
- `GET /api/agents/:id/transcript?before=&after=&limit=&kinds=`: chunks by `seq`; `after` and `lastSeq` (persisted, as above) are `transcript.subscribe`'s `since`.
- `GET` / `PATCH /api/settings`: `SettingsService` (§2.2); 400 `invalid_body` / `invalid`, 403 `remote_settings` (§8), 409 `env_override`.
- `GET /api/preflight[?refresh=1]`: each adapter's optional `preflight()` (never throws), cached 30 s, concurrent callers share a run, a refresh reruns it at most once per 5 s. The Claude adapter runs `claude --version` and `claude auth status` (JSON, read even on a non-zero exit) with the agents' allow-listed environment (`INHERITED_ENV`) and a 10 s timeout, reports the SDK version and the bundled CLI's (`manifest.json`); without a global `claude` it asks the SDK's bundled binary and reports a warning, not an error. The email and organisation are not passed on.
- `GET /api/notifications?after=&limit=`: the log through the protocol's pure `notificationOf`, which the client also folds over the live stream, so ids match and dedup across reconnects is by id. The scan reads only the notifying shapes (indexed `type` plus the payload fields that decide); a backfilled question that is no longer open is left out; the returned `seq` (the next `after`) is never below the `after` given. "Work interrupted by a restart" keys on `recovery.needs_attention{agentId, reason}`, which `AgentRuntime` logs once per interruption when recovery passes an agent over or cannot resume it, when a resumed session is lost before its first turn with no fresh fallback, or when that fallback fails — never on `agent.interrupted`, which every graceful shutdown and session reset logs.
- `GET /api/history/work?before=&q=&kind=&state=&limit=` and `GET /api/history/questions?before=&q=&kind=&status=&limit=` (P25-10, SPEC decision 61; `runtime/history-view.ts`): finished and archived projects and tasks (`state IN ('completed', 'failed', 'archived')`) and answered or cancelled questions as the domain tables hold them (a cancelled question also gets the `reason` of its last `question.cancelled`). Newest first by (`updated_at`, `id`), paged back by an opaque cursor `<updatedAt>~p|t|q<id>`; work merges the two tables by (`updated_at`, `t` before `p`, `id`), like the conversation endpoint. Each list reads a partial index of migration 0008, `(updated_at, id) WHERE <the list's term>`, named with `INDEXED BY` (SQLite otherwise picked `questions_status` and sorted; a query-plan test guards it), and a cancelled question's reason is read through 0008's `events_type_question` (`events(type, json_extract(payload,'$.questionId'))`); so a page without a search reads only its rows. A search is a `LIKE … ESCAPE '\'` substring match (case-insensitive for ASCII). Text comes back as the stream carries it: agent text was redacted when logged, user text is not (§8). The client renders the stream's current copy of a row's item when it has one. A malformed or foreign cursor (here and on `/conversation`) is a `CursorError`, answered 400 `invalid_query`. **Trails and holder chains (P5-03).** Each work row also carries `bodyName` and a `trail` derived from the log for the whole page in one read: `closedAt` (the last move into `completed`, `failed` or `moved`, while the work is still finished), `archivedAt` (while archived), `reopenedAt` (the last move out of a finished state), `moves` (each `body.moved` of the item, with `intoProjectId` for a task that joined a project, and a project task handed to another project via `task.updated` with a new `projectId` — the `task.updated` and `body.moved` of one command are folded into one move; body and project names resolved by the server), `promotedTo` (the project whose `meta.promotedFrom.taskId` is this task) and `promotedFrom` (a project's `meta.promotedFrom`). Each past question carries `holders`: the holder it was routed to when asked (the first `question.escalated` / `question.reassigned`'s `from`, else the row's holder), then one step per escalation or reassignment (with its reason), from 0008's `events_type_question`. Both fields are optional in the schema, so a client reading an older server still parses. Migration 0009 indexes these reads: `events_work_subject`, a partial expression index on `coalesce($.projectId, $.taskId, $.host.id)` `WHERE type IN ('project.state_changed', 'task.state_changed', 'task.updated', 'body.moved')` (other events pay nothing; the read names it with `INDEXED BY`, since the planner otherwise takes `events_type_question` for the `type IN` term), plus `projects(parent_project_id)`, `projects(json_extract(meta, '$.promotedFrom.taskId'))`, `agents(project_id)`, `agents(task_id)` and `questions(origin_agent_id, updated_at)`. A page's ids are bound as one JSON array (`IN (SELECT value FROM json_each(?))`), so one prepared statement serves every page size; a query-plan test checks each statement searches its index and scans no table.
- `GET /api/history/work/:kind/:id` (P5-03, SPEC decision 61; `HistoryView.detail`): one project or task inspected from the history, in any state (a moved-to link may lead to live work). Returns the row, `bodyName`, the trail, every state change oldest first (`{at, from, to, by?}` from its `*.state_changed`), its project (a task's, or a sub-project's parent), a project's tasks and sub-projects, the agents that ran it (a project's: its own by `agents.project_id` plus every agent of its current tasks by `agents.task_id` — a Steward of a standalone task that joined the project may carry no `project_id`; a task's: `agents.task_id`) and the questions those agents asked, newest first, at most 50 (`moreQuestions` when there are more), each with its cancel reason and holder chain. 400 `invalid_query` for a kind other than `project` / `task`, 404 `not_found` for no such row; bearer-guarded; rows as the snapshot holds them (redaction parity, tested).
- `GET /api/history/events?projectId=&from=&to=&after=&limit=` (P4-07; `runtime/history-events.ts`, typed in `packages/protocol/src/replay.ts`): the log's events that touch one project, oldest first, paged forward by `seq` (`{events, seq, hasMore, membership}`; `seq` is the next `after`). Membership is decided from the tables as they are when a read starts — the first page caches the members under the `membership` token (32 slots, 10 min) and later pages that pass it back reuse them, so one read's pages agree; work that has since *left* the project is not a member, so its past there is missing from the replay (known limit): the project and its sub-projects (transitively), their tasks, agents working on them, those agents' questions, the plan cards whose `meta.plan.projectId` is one of them, and the bodies they live on plus every body the log ever assigned them or moved them from or to (`body.assigned` / `body.moved`, read through `events_type`). An exhaustive switch (`touches`) keeps each event type to the right ids (`body.freed` by body, `question.*` by question, `agent.*` by agent…); `REPLAY_SKIPPED_EVENT_TYPES` leaves out what draws nothing (`message.*`, `control.*`, `permission.decided`, `recovery.needs_attention`, `agent.processes_stopped`). No server-side snapshot: the client folds from the log's start, because a project's events are a small slice and one fold implementation (the client's, held to the tables by the conformance test) is better than two. `from` / `to` only filter by `at`. Each request reads one rowid window (`id > after AND id <= after + 20 000`, `SEARCH events USING INTEGER PRIMARY KEY`, a query-plan test guards it) and parses only rows of kept types, so a request is bounded and a whole project walks the log once: 1 000 000 events, 5 % of them the project's, read in 51 pages, 0.8 s in all, 19 ms the slowest page — no index added. Rows are returned as the stream sends them (redacted when logged). 404 `not_found` for an unknown project.
- First-run marker (P25-08, SPEC decision 60): `SettingsPatch.setupCompleted: true` stamps `setupCompletedAt` (ISO) in `config.json` once; it is never moved or cleared. `SettingsResponse.setupCompletedAt` reports it, and `ConfigFile` / `ServerConfig` carry it. Only local requests may set it (it is not in the remote-writable list), so a remote client gets 403 `remote_settings`. `SettingsResponse.writable` (`all` | `limited`, from the same `writableFor` rule the PATCH applies; absent from an older server means `all`) tells the client whether it may finish the setup. The web client shows its wizard only for a valid settings reply without the marker and with `writable: 'all'`; a hand-edited marker is read leniently (any non-empty string; reported as ISO) so it never stops the server.

**The chat (P25-03; SPEC decisions 54, 55).** The client keeps its threads in their own store (`apps/web/src/state/conversation.ts`), a REST-filled cache beside the stream-derived `useAppStore`. It merges the history pages with the live `message.sent` and `text` chunks by entry id. The transcript is subscribed after the first page, from its `lastSeq` (the session's `transcriptSince` takes the max of the buffer's last chunk and the open chat's `lastSeq`). After a snapshot catch-up, or when a chat is reopened or the log changes, the thread pages forward from its newest history cursor — or rereads the newest page when it has none (a thread with only live entries); past 20 forward pages it restarts from the newest page, dropping older held lines (paged back in on demand), so it never leaves a hole. `message.sent.turn` marks a brain's turn prompt (`AgentRuntime.send({turn})`, set by the runner); the conversation endpoint's SQL leaves those out (`json_extract(payload,'$.turn') IS NULL`, still served by migration 0007's partial index) and so does the client. Cards are placed in a thread by `createdAt`; a Steward view that has paged back is exempt from the live transcript cap (`MAX_TRANSCRIPT`) until it reads its newest page again; a Steward's question is routed to its supervisor by role and project, not by its `supervisorId`, so a replacement Waykeeper's thread shows it. The Harmonizer's thread also shows a project's clarification the user holds or answered (`reachedUser`).

**Shared cards (P25-06).** Question and proposal cards are store-driven components keyed by id (`QuestionView`, `ProposalView` in `apps/web/src/panel/cards/`), rendered by the inbox, the chat thread and the ops console over `world.questions` / `world.proposals`, so an answer anywhere resolves everywhere with no client-side coordination: `question.answered` (or the proposal's decision) on the stream is the only signal. The Steward view renders permission questions through the same `QuestionCard` and its clarification box with the shared stale line and banner. Every card needs an `ApiContext`; the panel also provides `CardLinksContext` so agent names carry an "open agent" link.

**Desktop notifications (P25-07; SPEC decision 59).** In `apps/web/src/panel/notifications/`. `createNotifier` is wired in `startSession`, next to the store, and folds each message after the store applies it, through the protocol's `notificationOf` with lookups into the client world (the same function as `GET /api/notifications`, so ids match). A per-browser ledger in `localStorage` (`galactic.notifications.ledger`: `logId`, last `seq`, the last 500 ids) dedupes by `seq` and by id across reloads and tabs; the `Notification` `tag` is the id. A snapshot of a log the ledger has not seen sets the baseline and backfills nothing; a snapshot of the same log past the ledger's `seq` backfills `GET /api/notifications?after=` (at most 10 pages of 100, items at most 24 h old, 5 shown plus one summary). A tab decides on the current stored preferences (re-read at decision time, `storage` events) before it claims an id, so a tab with stale preferences cannot swallow a notification; once a ledger write throws (quota, private mode) the ledger lives in memory for that page. Dedup between tabs open at the same moment is best effort; the shared `tag` collapses a duplicate in the OS. Preferences (`galactic.notifications.prefs`: `enabled`, per-kind booleans) are per device and never sent to the server. `Notification.requestPermission` is called only from the Enable button's click.

**Settings page and first-run wizard (P25-08; SPEC decisions 51, 60).** In `apps/web/src/panel/settings/`. The page and the wizard share one `SettingsProvider` per panel and one spec per setting (editor, client check, patch), so both validate and word refusals the same way; the server stays the authority. `ApiError` carries the error body, which holds the zod `issues` of a 400.

**Managed agents, controls strip and project rows (P4-09; SPEC decision 69).** The side column's managed-agents section can be hidden per browser: `useManagedAgentsVisibility` (`apps/web/src/panel/managed-agents-visibility.ts`) keeps the choice in `localStorage['galactic.panel.managedAgents.visible']` (`'0'` hidden, anything else shown), every access in try/catch like `galactic.scene.visible`. Hidden means unmounted; the grid gets `pnl-grid-no-agents` and reflows, the inbox always stays. The control actions are shared UI in `apps/web/src/panel/controls.tsx` (`useControls`: `POST /api/control`, the inline confirmation of the destructive ones, the edit form, the refusal as an alert): the cards use it, and so does the **controls strip**, shown whether or not the cards are, which keeps the selected agent's own controls in the main area: in a Waykeeper's header its project's work actions and its agent actions, in a Steward's view its task's work actions beside the view's agent controls. Pause / resume are inline, the rest in a "More" menu. A project row's Steward count (`stewardCount` in `nav-model.ts`) counts by task: the project's own non-archived tasks that have had a Steward (total), and those whose newest Steward (`primaryAgent`) is live and not paused (active), shown "N active, M in total". Phone-menu items that close the menu after acting carry `data-closes-menu`.

**Hidable inbox, closed work and row actions (P4-12).** The inbox hides per browser like the managed agents, in `localStorage['galactic.panel.inbox.visible']` (`'0'` hidden, try/catch). Its state is a small module store (`apps/web/src/panel/inbox-visibility.ts`, `useSyncExternalStore`; cached only while something is subscribed, so a fresh mount reads storage again) rather than component state, because `revealInbox` / `revealQuestion` (`inbox-reveal.ts`; the top bar's "N waiting for you", a button in both bars, and the scene's beacons) are not React: they call `showInbox()` first, then look for the inbox or the card over a few frames as before. The grid gets `pnl-grid-no-inbox` with only the managed agents left; with both sections hidden the side column is not rendered and the grid is `pnl-grid-no-side` (`nav | centre`; stacked: scene, then the navigation full width). The wide bar offers "Show inbox" only while it is hidden; the phone menu always has the toggle (`data-closes-menu`). The navigation (`buildNav`) builds the whole tree, then prunes **closed** items — `completed` and `archived` (`CLOSED` in `nav-model.ts`; `failed` is not closed) — with everything nested in them, unless "Show closed" (`localStorage['galactic.panel.nav.showClosed']`, `'1'` shown) is on; the item holding the selected agent survives the pruning with its path (a deep link); `hiddenClosed` counts the pruned roots for the toggle's "(N hidden)". Closed rows carry `is-closed` (dimmed). Each row has a "⋯" button (shown on hover/focus, always on `(hover: none)`) that opens `NavRowActions` (`nav-row-actions.tsx`) inline under the row — inline, not a popover, because the navigation is a narrow scroll container: `workActions` minus edit through `useControls` (`POST /api/control` on the row's task or project, the same confirmations, the server's refusal as an alert), plus a note when a project has unfinished tasks (the server archives a project only when its tasks are finished; closing leaves them as they are, cancelling marks them failed). The Steward count's option is now `showClosed` (archived tasks still drop out of the total without it; completed ones count).

**Panel layout and the docked conversation (P4-10).** The shell (`.pnl`) is exactly the viewport (`height: 100dvh`, `overflow: hidden`): the top bar, then `.pnl-body` (`flex: 1 1 0; min-height: 0; overflow-y: auto`, where the settings, history and first-run pages scroll), then the grid (`flex: 1 1 0; min-height: 0`, one `minmax(0, 1fr)` row — no grid row has a fixed length). A drag writes `--pnl-dock-size` and `aria-valuenow` straight onto the elements on each pointer move and sets React state once, when it ends; the scene area, the navigation and the side column are memoised, and the R3F `Canvas` debounces its resize (`resize={{ debounce: { resize: 50, scroll: 50 } }}`), so a drag neither re-renders the panel nor resizes the renderer and composer on every frame. Minimised, only the bar is left: the body stays mounted and laid out, collapsed (`height: 0; visibility: hidden`, never `display: none`, which drops a scroller's position) and `inert` + `aria-hidden`, so the thread, its scroll position (the thread also restores the last position the user left it at when its box regains height) and its subscription survive. Composer drafts live in the conversation store per agent (`drafts`, cleared on send), so switching agents or remounting the chat keeps them. The landmark is named after who it is about ("Conversation with Harmonizer", "Steward · …"). The Waykeeper controls strip's "More" menu measures where it fits when it opens: below its row unless there is less room below than its height and more above (a minimised bar at the bottom, the stacked layout), capped to that room and shifted sideways to stay on screen (`placeMenu` in `controls.tsx`, `data-placement`). The scene's overlays are children of `.pnl-scene`, so they stay in the scene's (smaller) box. In list mode on a wide screen the dock is the whole centre and does not minimise. At or below 1100 px React renders a different tree: one scrolling `.pnl-stack` (scene, navigation, side column) above the dock, which minimises there in list mode too (its bar sits above the bottom safe area the shell pads for); crossing the breakpoint remounts the scene and the chat (a draft survives, being in the store). Open/minimised and the height are per browser in `localStorage['galactic.panel.dock']` (`{open, size}`, read and written in try/catch, validated and clamped on read; a drag is saved when it ends). The chat thread is `flex: 1 1 0; min-height: 0` inside the dock (the old `max-height: calc(100vh - 290px)` assumed a full-height column and pushed the composer out of sight in a shorter one), and keeps to the bottom when its box changes height (a `ResizeObserver`), as when the dock is resized or restored.

## 8. Security

- The server can start processes on your machine. It must require a bearer token even on localhost, sent in the first WebSocket frame (§6.3) or an `Authorization` header for REST, and it must bind to `127.0.0.1` by default; Tailscale Serve terminates TLS and forwards to it.
- **`Host` allow-list** (`localhost`, `127.0.0.1`, the `*.ts.net` name) and an **`Origin` check** on every WebSocket upgrade, so a web page in the same browser cannot reach the server via DNS rebinding or cross-origin sockets.
- The token is printed once by `galactic start` and pasted (or scanned as a QR code) into the phone PWA; Tailscale identity headers may replace it for remote clients in Phase 7. `GET /health` hands it out only to a request `isRemoteRequest` calls local: from loopback, with a loopback `Host`, no forwarding or Tailscale headers, and an `Origin` that is absent or a loopback name. A proxy on this machine (Tailscale Serve, `vite preview --host`) connects from loopback too, and a plain GET or curl through it sends no `Origin`, so the remote `Host` is what withholds the token (P3-08 review: the Origin check alone handed it to any LAN client).
- Development-only routes (`/dev/*`) exist only with `GALACTIC_DEV=1`; they are bearer-guarded and refused to remote clients (403 `remote_dev`, `isRemoteRequest`: like a settings write, a development tool belongs to this machine, P4-06); they never write domain rows without the matching events, so a replaying client and a snapshotting one always agree. The scene harness (`/dev/harness/*`, P4-06) writes only through `Commands` and the runtime's agent events, flags what it creates `meta.harness`, refuses anything else (409 `not_harness`), and its "clear" stops its fake agents and archives its tasks and projects, never touching real ones.
- **Agent processes get an allow-listed environment** (`INHERITED_ENV` in the supervisor: PATH, HOME, locale, proxies, `CLAUDE_CONFIG_DIR`, …) plus what the spawn passes explicitly; the server's own variables — its token, any API key — never reach an agent unless a spec hands them over (bare mode does, for its key).
- **REST authentication runs on the decoded route** (P1-28): the `/api` and `/dev` routes live in encapsulated Fastify scopes whose `onRequest` hook checks the bearer token, so no spelling of the path (`/%61pi/…`) reaches a handler without it.
- Permission requests from agents follow the per-project policy table (SPEC §3.6); anything not auto-allowed is surfaced to the user and never auto-approved for a remote client unless explicitly configured. **The policy engine is lexical, a guard rail rather than a sandbox** (P1-30): `domain/permissions.ts` lexes a subset of bash (quotes removed as the shell does, `&`/`;`/`|`/newlines, glued and fd-prefixed redirections, command substitutions classified as commands, heredoc bodies as data, brace expansion capped at 64 alternatives); a command name or git subcommand built at run time, `$'…'` quoting, an interpreter reading from stdin or a heredoc, and `git -c` keys git executes are opaque. An opaque command — like an unknown tool — is *unclassified* (`Classification.unclassified`): it gets the policy's `unclassified` decision (absent or unknown = `ask`; `allow` only in the `trusted` preset, SPEC decision 49) on top of the categories the engine still saw in it, and its raw text is searched for a push (`mentionsPush`: `git` followed anywhere by the word `push`, also with quotes and backslashes removed, plus the push rules), so a trusted project still asks before `sh -c "git push"` or `python - <<EOF … subprocess.run(['git','push'])`. By design it does not follow symlinks and does not see what a script written in one call does when run in the next (`Write x.sh` → `bash x.sh`, `npm test` after editing `package.json`); an OS-level sandbox (Claude Code's sandbox, seatbelt) is the real boundary if one is needed. The gate never throws (an exception is a `deny`), an invalid policy makes every action `ask`, and a cwd outside the workspace (or a workspace of `/`) makes every call `ask`.
- **Credentials reach the CLI's tools.** The `claude-sdk` adapter passes `CLAUDE_PASS_ENV` (login and API routing: `CLAUDE_CODE_OAUTH_TOKEN`, `ANTHROPIC_AUTH_TOKEN`, Bedrock/Vertex keys, …) to the CLI because it needs them; every shell child of the agent can therefore read them. Accepted for a local single-user tool; revisit with a sandbox.
- Known secret patterns (API keys, tokens, private-key blocks, case-insensitive `password`/`secret`/`api_key`/`token`-style assignments, Basic auth, Slack, GitLab and Hugging Face tokens) are redacted from transcripts before persisting and before sending to any client, from every string of the other agent events, and from the error messages of `/api` 409 responses (P1-31, P1-38); the routes over `DomainCommands` (`/api/control`, `…/decide`, `…/answer`) answer an error that is not a domain refusal with a 500 `{error: internal}`, logged and never echoed. **Text the user (or a supervisor) writes is not redacted**: `message.sent.text`, `question.answered.answer` and the spawn prompt in `Agent.meta` are stored and broadcast as written — a key pasted into a message stays in the log.
- Store API keys in the OS keychain or a `.env` outside the repo; never send them to the browser.

---

**Server-run git (P2-05).** The server runs git only through `workspace/git.ts`: `execFile` with argument arrays (never a shell string), `-c core.hooksPath=/dev/null -c core.fsmonitor=false`, an allow-listed environment, no prompts (`GIT_TERMINAL_PROMPT=0`) and a 60 s timeout. Hooks are off because the server's own `worktree add`, merge and initial commit would otherwise run repository hooks on the server's behalf, outside any agent and permission gate; Stewards' own commits run in their shell, with hooks, under the project's policy. Git work on one repository is serialised in-process. `mergeTask` tells a conflict with the project's own work from one with external changes (SPEC decision 30): the base side is `rev-list --full-history --no-merges <merge-base>..HEAD -- <conflicting files>`, and a commit is the project's own when a merge of one of its tasks brought it in (any `before..commit` of the task's `Task.meta.merges`, appended on every successful merge; `meta.merge` is the last); the rest are `externalCommits` (short id, subject, author; at most 20, `externalCount` in all). It fails closed: a base side git cannot list makes the conflict external (`externalUnknown` says why), so nobody is sent back on a guess. Known limit: merge commits are skipped (`--no-merges`), so a hand edit made inside a merge commit on the base branch is not seen as external by itself. Workspace paths are canonicalised (symlinks resolved) and refused when they are `/`, the home directory, the projects root, or touch the data directory. Values a brain can write (`Task.branch`, `Task.meta`) never reach git unchecked: the worktree root is always derived from the workspace and the task id, and a stored branch must be a valid `galactic/…` ref name. Known gap: filter drivers configured in the repository's shared `.git/config` (which a Steward's shell can edit) still run for the server's `git status` / `add`; the permission table counts anything under `.git/` as outside the workspace (decision 22), which is the guard for now.

**Remote clients (P2-04).** `isRemoteRequest(req)` counts a request as local only over a loopback connection with a loopback `Host`, no non-loopback `Origin`, no forwarding header (`Forwarded`, `X-Forwarded-*`, `X-Real-IP`) and no Tailscale identity header; everything else is remote — headers can only make a request look more remote. `autoApproveRemote` (`config.json` or `GALACTIC_AUTO_APPROVE_REMOTE`) is off by default; while off, a policy a remote client chooses is floored at the global default with `noLooserThan` (the stricter of the two per category) — on every `permissionPolicy` write: `policyForWrite(policy, {origin, autoApproveRemote})` (`domain/permissions.ts`) guards `createProject`, `updateProject`, a project `control` edit, the `POST /api/agents` presets (P2-21) and the trust level an approved proposal card gives its new project (`decideProposal(…, write)`, P2-22). The floor covers `unclassified` too (the stricter of the two, `ask` when either is absent), so a remote client can never make a project `trusted`; the card's level itself (`meta.trust`, folded by `foldProposalMeta` on server and clients alike) is set only by a user decision. The command surface takes an optional `WriteOptions {origin: 'local' | 'remote'}` last argument and a missing origin counts as remote; the REST routes pass `originOf(req)`, and `POST /api/agents/:id/send` records it on `message.sent.origin`, so a brain acting on a user's message writes with that origin (`originOfMessages` over the turn: local only if every message is). A remote answer to a permission question is an explicit user decision and is accepted. The global default table is a setting (P25-01, SPEC decision 50): it lives in `domain/permissions.ts` (`globalDefaultPolicy` / `setGlobalDefaultPolicy`, process-wide, set at startup from `config.json` and by `PATCH /api/settings`), and every merge (`resolvePolicy`) and floor (`noLooserThan`) reads it. A remote `PATCH /api/settings` of it goes through `policyForWrite` against the current default, so it can only tighten (reply `floored: true`); a remote reset to the SPEC table is floored too. Every other setting is local-only (decision 51): unless `autoApproveRemote`, a remote or unknown-origin patch touching anything but `qualityTier` and `defaultPermissionPolicy` is refused with 403 `remote_settings` before anything is written.

## 9. Alternatives considered

| Area | Alternative | Why not (for v1) |
|---|---|---|
| Frontend | Angular + Three.js | Much smaller 3D ecosystem; manual scene plumbing; change detection vs render loop. Fine for the side panel, poor for the scene. |
| Frontend | Svelte + Threlte | Excellent, lighter than R3F, but smaller community and fewer ready-made helpers/examples. Good second choice. |
| 3D engine | Babylon.js | Batteries-included engine with good tooling, but weaker React integration and fewer solar-system references. |
| Renderer | WebGPU (+ WebGL2 fallback) | Different material system, fewer ready-made effects/helpers, two render paths to test; nothing in v1 needs it. Revisit for GPU-driven simulation. |
| Desktop | Electron | Heavy; unnecessary because the server is already a separate process. Tauri 2 wraps the same UI if a shell is wanted. |
| Backend | Python (FastAPI) | Fine for the brains, but you would lose shared types and the TypeScript Agent SDK / ACP SDK ergonomics. |
| Claude transport | ACP (`claude-agent-acp`) on day one | Second Claude integration next to the SDK the brains need; cost/resume/spawn options depend on what the ACP adapter exposes. Becomes the path for Codex/Gemini later. |
| Agent integration | Prompt-only orchestration (agents talk to each other via files or messages) | Untraceable, fragile, expensive. Tool-armed brains + a real event model are simpler to debug. |
| Remote access | Cloudflare Tunnel + Access | Great if you need public-internet access with SSO; more setup than Tailscale for a single user. Keep as option. |
| Remote access | ngrok / raw port forward | Public URL with weak or no auth in front of a process-spawning server. No. |
