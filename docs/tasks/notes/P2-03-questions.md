# P2-03 — Question service

## What was built

- `apps/server/src/domain/question-service.ts`: where questions go. Everything runs inside a command (one write rule).
  - **Open** (`openFromNeedsInput`, `openRouted`): a permission question is held by the user (`holderFor`); a clarification goes to the origin agent's **first living supervisor** up the `supervisorId` chain, else the user (`livingAbove` in `questions.ts`). The context gains `origin: {role, taskId?, projectId?, bodyId?, recent[]}`: the origin agent's last `RECENT_EVENTS = 10` logged events as `{seq, at, type, summary?}`. The summary is the tool name, progress summary, question text, message text, result or error, capped at 200 chars and already redacted by the log.
  - **Escalate**: `escalateQuestion(ctx, id, by, isLiving)` moves the question to the next *living* supervisor, else the user. Without `isLiving` it behaves as before (the bare P2-01 command).
  - **Answer / cancel**: `question.answered` and `question.cancelled` carry `holders: Id[]`, which lists every agent that ever held the question, oldest first. The list comes from the log's `question.opened/escalated/reassigned` plus the current row (`holdersNow`). First answer wins and the "already answered by …" refusal is unchanged (P2-01). The runtime still hands the answer to the origin agent's adapter before the log records it.
  - **Orphans** (`endAgentQuestions` → `rerouteHeldBy`): when an agent ends (finished / failed / stopped / interrupted), its own open questions are cancelled (P1-34, now naming their holders). Each open question it *held* moves with `question.reassigned{reason: "holder <id> <how>"}` to the next living supervisor above it, or to the user. A re-parented chain never hands a question back to its origin.
  - **Liveness** (`QuestionRouting.isLiving`): `composeRuntime` uses the status store (an agent with a record that is not ended). `Commands` without a runtime falls back to the log (the agent's last lifecycle event is `agent.spawned`). The dying agent counts as dead in its own end command, before any projection has folded it.
- Wiring: `AgentRuntime` (needs_input routing, holders on answer and on withdrawal, end and recovery re-routing), `Commands` (`recordAgentEvent` now also cancels and re-routes on an end event, `openQuestion` is routed, `answerQuestion` names holders, `escalateQuestion` is liveness-aware), `composeRuntime` (one routing shared by both).
- Protocol: `QuestionOrigin`, `QuestionRecentEvent`, `QuestionContext.origin?`, and `holders?` on `QuestionAnswered` and `QuestionCancelled`. Fixtures were extended. The reducer needs no change: `origin` travels inside `question.opened`, and `holders` is not part of the row. No migration: `context` is a JSON column.
- Tests: `question-service.test.ts` has 13 tests. They cover routing to the Waykeeper with origin context, skipping a dead supervisor, the user when nobody is alive, permission questions staying with the user, the project chain (Steward → Waykeeper → Harmonizer → user, answer delivered and Steward finishes), escalation skipping a supervisor that died, the asteroid chain (Harmonizer → user), the double answer, a non-holder answer refused, holders on cancel, an orphaned holder (Waykeeper then Harmonizer stop), shutdown order, and log-only routing through `recordAgentEvent`. The conformance walk now opens a routed question and covers a dead holder's re-route.

## Decisions (proposed text, ready to paste)

**SPEC §7, new decision — Question routing and notification.** A clarification question is held by the asking agent's nearest *living* supervisor (Waykeeper for a project Steward, Harmonizer for an asteroid Steward or a Waykeeper), else by the user. A permission question is held by the user from the start. Escalation and orphan re-routing follow the same rule. An agent counts as living from `agent.spawned` until it finishes, fails, is stopped or is interrupted. A restart therefore sends a question held by an interrupted supervisor up the chain. When a question is answered or cancelled, every agent that ever held it is named on the event, and those agents' mailboxes are told so they stop waiting.

**TECHNOLOGY §5.3, append.** *Question service (P2-03, `domain/question-service.ts`).* `agent.needs_input` → `openFromNeedsInput`: holder = first living ancestor by `supervisorId` (permission → user). `context.origin = {role, taskId?, projectId?, bodyId?, recent: last 10 events of the agent {seq, at, type, summary?}}`. An agent's end (the runtime's `recordEnd`, startup `recover()`, `Commands.recordAgentEvent`) runs `endAgentQuestions` in the same command: it cancels the agent's own open questions and re-assigns the ones it held (`question.reassigned{reason: "holder <id> <how>"}`). `question.answered` and `question.cancelled` carry `holders[]`, every agent id that held the question, oldest first. P2-06 feeds `question.answered/cancelled` to the mailbox of each id in `holders`, and `question.opened/escalated/reassigned` to the mailbox of the new holder (`question.holder` / `to`), skipping events the brain caused itself. Liveness comes from the status store in the composed runtime, and from the log's lifecycle events otherwise.

## Deferred / for later tasks

- **P2-04**: the policy evaluation goes in front of `holderFor` for `kind: permission`, in `openFromNeedsInput` or before the runtime opens the question. Today a permission question is always user-held, so it never reaches a brain.
- **P2-06**: mailbox subscription rules as above. `holders` includes the answering agent itself, so the mailbox drops self-caused events.
- **P2-16 (hierarchy resume)**: resume supervisors before their Stewards. Otherwise a resumed Steward re-asks while its Waykeeper is still `interrupted`, and the question goes up a level. At shutdown, questions held by interrupted supervisors move up (eventually to the user) before their Stewards' interruption cancels them. That is noisy but correct.
- **Re-parenting** (`updateAgent{supervisorId}`) does not move questions the old supervisor holds. A hand-over (P2-12 promotion) should call `reassignQuestion` explicitly.
- **A holder revived by resume** does not get its questions back: they stay with whoever took them.
- **Performance**: `recentEvents`, `holdersOf` and the log-based `isLiving` use `json_extract` over `events` (the newest-first scan with `LIMIT` is cheap; `holdersOf` scans the whole table once per answer or cancel). If the log grows large, add an expression index (`json_extract(payload,'$.questionId')`, `'$.agentId'`) in a migration.
- Corner case 10 (an answer after the agent stopped is stored and fed on resume) still follows decision 21 (cancelled, re-asked).
