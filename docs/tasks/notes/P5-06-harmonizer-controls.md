# P5-06 — Controls for the Harmonizer

SPEC decision 82 (Cosmin, from P5-05's checklist row §4.2.42h / follow-up F2): the Harmonizer's dock offers Pause and Resume like any agent's, and a confirmed **Restart Harmonizer**; never a plain Stop; "Resume session" only for an interrupted Harmonizer.

## What was built

### Server — `POST /api/harmonizer/restart`

- `apps/server/src/brains/harmonizer/restart.ts` — `harmonizerRestarter(host, opts)` returns the restart function; `index.ts` wires it with the boot runtime (`GALACTIC_HARMONIZER`), the projects root and the Harmonizer's deps, and passes it to `buildApp` (`restartHarmonizer`), which registers the route in `http/agent-routes.ts`.
- Sequence (revised after the wave-3 review): the whole restart holds the Harmonizer lock (`withHarmonizerLock` in `index.ts`: one start per runtime at a time, shared with the boot start and `keepHarmonizer`, so one Harmonizer is structural) → the live one is **stopped first** with `by: user` and nothing else happens unless it ended (a stop that throws leaves it running and still driven by its runner; the route answers 500) → its tool-asked user questions (`ask_user`, `ask_confirmation`: clarification, `meta.source: command`, not a project's closure question), which the stop ends, are named in the new one's first turn; one still open after the stop is withdrawn as the user (the user started the restart) → `startHarmonizerLocked` starts a fresh one on the same runtime and working directory. A start that fails is retried **once on the boot runtime** (what `keepHarmonizer` would start), reported through `onError`; if that fails too the error goes to the route (500).
- **One live Harmonizer:** the old one is stopped (and gone from `liveAgents`) before the new one is started; the user's stop means `keepHarmonizer` does not start another one beside it; a second restart while one is under way, or while an interrupted Harmonizer is on its way back (`runtime.isReserved`), is refused (409). `startHarmonizer`'s live check ignores scene-harness rows.
- **Restart window:** at most 3 restarts per 10 minutes (like `keepHarmonizer`'s); past it `RestartLimitError` → 429 with `Retry-After` and "try again in N min". A Harmonizer's spawn is not counted in the per-hour spawn window (`CapsEnforcer.noteSpawn` skips the role; decision 43), so restarts never block Steward or Waykeeper spawns — before the fix ~30 restarts filled the global window for an hour.
- **Questions (decision 45):** asked questions as above; the closure question is cancelled with the stop and `closureNotes` relays the closure request again; questions the old one *held* (a Waykeeper's, escalated) move on as on any stop (P2-03) — to the next living holder, i.e. the user.
- **An interrupted last Harmonizer** (not live): the fresh one starts beside its row; the interrupted one's own tool-asked questions are withdrawn by the new one's start notes (`strandedQuestionNotes`, `closureNotes`), and the questions it held move on to the user once the new one runs: `AgentRuntime.releaseInterruptedHarmonizers`, which every `startHarmonizer` that starts one calls — so `keepHarmonizer`'s replacement after an interruption no longer strands them either. The row stays `interrupted` (an ended status is a sink in the status store, so it cannot become `stopped`), like the Harmonizers startup recovery passes over, and it is not reopened while the new one runs (`refuseReopen`). Order chosen so there is never a moment with fewer live Harmonizers than before.
- **The user informed:** `StartHarmonizerOptions.notes` (new) puts lines first in the new Harmonizer's first turn, once: "the user restarted the Harmonizer from the panel: the previous one (…) was stopped and you are a fresh one, seeded from the database. Tell the user in one line that the Harmonizer was restarted and is ready".
- **Runtime choice:** the live one's; else the newest Harmonizer row's (one stopped from the ops console, interrupted or failed); else the boot setting; with none (`GALACTIC_HARMONIZER=off` and no Harmonizer ever) → 409 `refused`. The scene harness's dormant stand-in is never taken for the Harmonizer.
- **Auth decision:** bearer-guarded like every `/api` route, and open to any authenticated client (remote too), consistent with `POST /api/agents/:id/stop` and the panel's controls — it is a control action, not a settings write. Documented in TECHNOLOGY.md ("Restarting the Harmonizer").
- Protocol: `RestartHarmonizerResponse {agentId, replaced?}` in `packages/protocol/src/rest.ts`; web `api.restartHarmonizer()`. Errors: 409 `refused` for a refusal (`DomainError`), 429 past the restart window, 500 for anything else.

### Panel — the Harmonizer's dock bar

- `HarmonizerControls` in `apps/web/src/panel/controls.tsx`, rendered by `MainHeader` in `Panel.tsx` for the Harmonizer (keyed by its id): "Pause the Harmonizer" / "Resume the Harmonizer" (`POST /api/control` on the agent, via `useControls`), "Resume session" only while it is `interrupted`, and "Restart Harmonizer" (offered in every state, so the user is never left without one) behind an inline confirmation.
- The inline confirmation was factored out of `ControlFeedback` into `ConfirmBox` (same behaviour: focus on "Keep" — decision 81 — Escape keeps, focus back to the opener), now shared by the cards, the strip and the Harmonizer's controls.
- **Focus across a restart** (wave-3 review): "Yes, restart" moves focus to the dock bar's heading (`h1.pnl-title`, `tabIndex=-1`) while the restart runs (the Restart button is disabled meanwhile); the new Harmonizer's controls — a remount, keyed by its id — take it back on their Restart button (`RestartFocus`, kept by `MainHeader` between the two mounts, honoured for 30 s). A failed restart gives focus back to Restart and shows the reason (e.g. "try again in 4 min").
- No Stop and no "More" menu for the Harmonizer. The selection stays `{kind: 'harmonizer'}`, which resolves to the newest running Harmonizer (`currentHarmonizer`), so the dock follows the new id as soon as the stream brings it. Works with and without the scene (the dock bar is the same in both).
