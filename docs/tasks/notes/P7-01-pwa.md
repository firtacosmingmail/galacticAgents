# P7-01 — PWA manifest and service worker

Design: TECHNOLOGY §2.4 ("The service worker is hand-written, not `vite-plugin-pwa`").

## What was built

- `apps/web/public/manifest.webmanifest`: name "GalacticAgents — Mission Control", short name "Galactic", `display: standalone`, start URL and scope `/`, theme and background `#10131c` (the panel's slate); icons 192/512 "any", 512 "maskable" (drawing inside the 80 % safe zone), SVG.
- `apps/web/public/icons/*`: generated by `node apps/web/scripts/pwa-icons.mjs` (a blue planet, its ring and an amber satellite); `apple-touch-icon.png` 180 px for iOS.
- `apps/web/index.html`: manifest and icon links, `theme-color` for dark and light, the iOS standalone metas (`apple-mobile-web-app-status-bar-style: default`).
- `apps/web/src/pwa/sw.js` (the worker), `build-plugin.ts` (writes `dist/sw.js` in production builds only), `register.ts` (registration, update flow, install offer), `PwaNotices.tsx` (the notices), rendered beside `<App />` in `main.tsx`.
- Server: `apps/server/src/http/web-cache.ts` — `no-cache` on `sw.js`, the page and the manifest; a year, immutable, on `/assets/*`; an hour on icons; 404 rather than the page for a missing build file.

## Verified here

- Vitest: `src/pwa/sw.test.ts` (the worker run against a fake worker scope: precache, what it never touches, network-first page with offline fallback, cache-first assets, HTML never kept as an asset, version clean-up, the messages), `build-plugin.test.ts`, `register.test.ts` (dev/prod registration, silent vs. notice update, reload only after a requested takeover, update checks, install offer on touch only, iOS hint, dismissal remembered), `PwaNotices.test.tsx` (behaviour and axe: no serious/critical findings), server `app-static.test.ts` (headers, 404s).
- Headless Chrome (CDP) against a production build served by the real server on 127.0.0.1:47811 (`GALACTIC_HARMONIZER=off`), 20 checks: headers and content types; the worker activates; `Page.getAppManifest` has no errors and **`Page.getInstallabilityErrors` is empty** (Chrome's own installability check — what Lighthouse's former "installable" audit used); one versioned cache holding only shell files (nothing under `/api`, `/ws`, `/health`, `/dev`, `/debug`); a simulated deploy (new entry name, new `sw.js`) while the page runs shows "A new version of GalacticAgents is available", Reload lands on the new build and the old cache is gone; a second deploy picked up by a plain reload serves the new shell at once and the worker takes over silently, without a notice; with the server stopped, a reload still opens the cached shell (the panel renders, disconnected). The first run failed the in-page deploy step once (no notice within 10 s); four later runs passed every check and the cause was not found — worth watching on the device.
- Dev mode: Vite on another port (47813): no worker registration, the Vite client loaded, the page renders.

## Review fixes (2026-10-05)

- **First install vs. no controller** (`register.ts`). "Nothing to update" is now decided on `reg.active`, not `navigator.serviceWorker.controller`: after a hard reload (the page is uncontrolled) or before `clients.claim()` lands, a waiting worker used to be ignored. With an active worker and no controller the entry check runs as usual; Reload then reloads on `controllerchange` or when the new worker reaches `activated`, whichever comes first.
- **Two tabs.** Tab B taking the update silently activated the worker; tab A's `controllerchange` arrived unasked and was ignored, and A's Reload then posted `SKIP_WAITING` to a worker that was no longer waiting and never reloaded. Reload now reloads directly unless the worker is still `installed`.
- **Discarded worker logged.** A new worker that goes redundant without activating (failed install, or replaced by a newer one) is logged with `console.warn`; the page keeps its version silently otherwise.
- **Rebuild without restart** (`app.ts`). `@fastify/static` ran with `wildcard: false`, which lists the files at startup: a `pnpm build` while the server kept running 404'd the new assets (a blank page, and a worker whose precache failed). Now `wildcard: true` (a lookup per request, dotfiles ignored); the 404-for-build-files rule and the cache headers are unchanged and tested, plus a test that a file written after startup is served.
- **Live region.** Only the notice's message (`<p role="status">`) is announced, not its buttons; the empty `<p>` stays in the page so the announcement fires.

## Manual device checklist (Cosmin)

Prerequisite: P7-02's Tailscale Serve set-up (HTTPS on the `*.ts.net` name — workers and installation need a secure origin; `http://<LAN-IP>` will not do). `pnpm build`, then `galactic start`.

Android (Chrome):
1. Open `https://<machine>.<tailnet>.ts.net/`. After a few seconds the bottom notice offers **Install**; tap it, confirm. The Home Screen icon is the planet, on a circle/squircle without white edges (maskable).
2. Open from the icon: no browser bar (standalone), status bar slate-coloured. Paste the token (the installed app may not share the browser's storage).
3. "Not now" on the notice: it does not come back in that browser.

iOS (Safari, 16.4+):
4. Open the same URL in Safari. The notice says "tap Share, then Add to Home Screen"; do it. The icon is the planet (`apple-touch-icon`), the name "Galactic".
5. Open from the Home Screen: full screen, no Safari bar. Check the status bar in **both** dark and light appearance (style `default`; if it looks wrong, try `black-translucent`, the panel already respects the safe areas). Paste the token: a Home Screen app has its own storage on iOS.
6. "Got it" hides the hint for good in Safari.

Both:
7. Update: with the app open, run `pnpm build` on the Mac (a restart of `galactic start` is no longer needed; with the browser's devtools open, no "discarded before it activated" warning appears). Bring the app to the foreground (or wait ≤ 30 min): "A new version … Reload" appears; Reload shows the new build. Then deploy again, fully close and reopen the app: the new build loads without a notice.
8. Airplane mode, reopen the app: the shell opens (disconnected), no browser error page. Back online it reconnects.
9. `/debug` (ops console) still opens and is never served offline.

## SPEC text (now decision 91 in SPEC §7)

**Decision 91 — Installable app** (§4.6, §5, decisions 67, 81): the web app can be installed on a phone, a tablet or a computer and opens full screen from the Home Screen as "Galactic". On phones and tablets a small notice at the bottom offers the installation — the browser's install button, or on iOS "tap Share, then Add to Home Screen" — until it is accepted or dismissed in that browser ("Not now", "Got it"); computers keep the browser's own install button and get no notice. After a new version of Mission Control is deployed, an open app shows "A new version of GalacticAgents is available" with Reload and Later; Later hides it until the next load, which loads the new version anyway, without a notice. The app's page opens from the device's cache when Mission Control cannot be reached (it then shows the disconnected state); nothing else — conversations, questions, settings, the ops console — is ever served from a cache. The notices never take the focus and are announced politely. An installed app keeps its own storage on iOS: the token is pasted (or scanned, P7-02) once more there.
